# Refinar `engine-specs` usando rsdkv4-wasm como piloto

2026-08-13 · rama `feat/from-vanilla` · a partir de integrar la SDK en `src/craft`

## Qué pasó en la sesión

Enganchar el lanzador de `src/craft` a la SDK hizo aflorar cuatro tropiezos. Ninguno era un
bug de la SDK, y los cuatro son síntoma de lo mismo — la superficie del contrato no obliga
a nada y sus nombres colisionan con los de la extensión del motor:

| Síntoma | Causa |
| --- | --- |
| `NotFoundError` de OPFS al lanzar | `storageNamespace: \`rsdkv4/${this.selectedGame}\`` interpolaba el **objeto** del juego, no su `id` |
| Pantalla en negro con el motor corriendo | se pasó el `<canvas>` como `attachTo`; la SDK crea el suyo *dentro*, donde es contenido de reserva que el navegador no pinta |
| `instance.start(slot, player)` no hacía nada | `start()` es el no-op del contrato y se traga los argumentos; lo que arranca partida es `game.start()` |
| Siempre salía Sonic | se pasó `players[player]` (un **nombre**) donde el motor quiere el **índice**; la SDK hace `player \| 0`, y `'TAILS' \| 0` es `0` |

Los ejemplos de uso de la API **actual** quedan en [docs/SDK-examples.md](../docs/SDK-examples.md),
con cada uno de estos casos marcado como *Gotcha*.

## Estado de conformidad (verificado con `tsc`)

- `const _sdk: EngineSDK = { manifest, load }` **compila hoy**: la Layer B ya conforma
  estructuralmente. No hace falta refactor, hace falta escribir la línea.
- `interface X extends EngineInstance { pause(owner?: string): void }` también compila — un
  parámetro opcional de más es compatible con `pause(): void`, luego el `Omit<>` de
  [rsdkv4.sdk.ts:331](../src/rsdkv4.sdk.ts#L331) sobra.
- `const cfg: EngineConfig = { canvasEl }` **no compila**: `assets` es obligatorio en el
  contrato. Un host que sólo use `dataProvider` (craft, y el flujo que la propia SDK
  documenta) no tipa.

Contraste con los otros motores del ecosistema (`fbneo`, `mGBA`, `snes9x`, `jgenesis`,
`celeste`):

1. **Nadie declara conformidad.** `grep -rl "satisfies EngineSDK\|: EngineSDK =" */src/*.ts`
   → 0 resultados en los 10 repos, pese a que el README del contrato lo prescribe.
2. **Los assets perezosos están reinventados tres veces**: `dataProvider`/`settingsProvider`
   (rsdkv4), `romProvider` (jgenesis), `gameProvider` (celeste, que además acepta `Blob`).
3. **`purgeStorage()` devuelve `{data, settings}` en todos**, incluido mGBA, cuyos assets son
   `rom` y `bios`: la forma se copia aunque no describa lo que borra.

Contrato actual: `CONTRACT_VERSION = 0.1.1`, paquete npm `0.2.6`.

# Parte 2 — Contrato 1.0: la cadena

Rediseño acordado en sesión. Rompe a propósito: el objetivo del refinamiento es que los
fallos de arriba sean **imposibles**, no que estén documentados.

```js
const sdk = new Rsdkv4SDK()
  .assets({ data: () => file.arrayBuffer() })   // valor o thunk
  .config({ skipStartMenu: true })              // ↔ manifest.config
  .storage({ namespace: 'rsdkv4/Sonic1' })
  .on('error', (e) => console.error(e.error))
  .mount(parentEl)

const instance = await sdk.start({ slot: 0, player: 1 })   // ↔ manifest.start

instance.destroy()                     // un reset es esto…
await sdk.start({ slot: 2 })           // …y volver a arrancar desde la fábrica
```

## 2.1 Un solo `start()` en toda la API

El `sdk` es una **fábrica** y `start()` su método de fábrica: arranca el motor y devuelve la
instancia. La instancia **no** tiene `start()` ni `reset()` — resetear es `destroy()` y
volver a arrancar desde la cadena, que además permite reconfigurar por el camino (§2.2).

Con esto desaparece el choque `instance.start` / `game.start` que costó tres iteraciones de
la sesión: sólo hay un `start`, y está donde se lee que arranca algo.

El payload es opcional: sin él, `start()` sólo arranca y manda el menú nativo del motor.

**Reiniciar sin rearrancar:** `instance.reset(payload)` reinicia la sesión en caliente con
otros parámetros. Un reset a encendido *con* parámetros es exactamente lo que hace
`web_start_game(slot, player)` en RSDKv4 (milisegundos, sin tocar el wasm ni releer
`Data.rsdk`), y en un emulador es el power cycle de siempre con payload vacío. Así la vía
rápida es API del contrato en vez de un atajo no portable, y `reset()` deja de lanzar en
rsdkv4.

Un verbo por objeto: `sdk.start()` crea la instancia, `instance.reset()` la reinicia.
`destroy()` + `sdk.start()` sigue siendo la salida cuando además hay que reconfigurar
(cambiar de juego, de namespace…).

**Varias instancias:** `sdk.start()` con una instancia viva lanza, salvo que el motor declare
`capabilities.multiInstance` (por defecto `false`). En rsdkv4 nunca podrá: SDL localiza el
render target por `#canvas` y el contexto GL es del elemento.

## 2.2 Fases: la configuración se congela **mientras haya instancia viva**

No "después del primer `start()`": la fábrica tiene que poder reconfigurarse entre
ejecuciones, que es justo el caso útil del reset — `destroy()` →
`.storage({ namespace: 'rsdkv4/Sonic2' })` → `start()`, o sea cambiar de juego con la misma
cadena.

| método | sin instancia viva | con instancia viva |
| --- | --- | --- |
| `.assets()` `.config()` `.storage()` `.artifacts()` | configura | **lanza** — el FS está montado y el `settings.ini` escrito |
| `.mount(container)` | recuerda la caja | reparenta el canvas y reajusta |
| `.mount(canvasEl)` | fija la superficie de render | **lanza** — ver 2.3 |
| `.on(type, handler)` | registra | registra |
| `.start(payload)` | arranca y devuelve instancia | **lanza** salvo `capabilities.multiInstance` |

Que `.assets()` lance en vez de ignorarse en silencio es deliberado: es la misma clase de
fallo que un `settings.ini` persistido ganándole a `config` sin decir nada.

## 2.3 `mount()`: la SDK posee el elemento, el host posee la colocación

```ts
readonly canvasEl: HTMLCanvasElement;   // creado en el constructor, desprendido
mount(target: HTMLElement | HTMLCanvasElement): this;
```

- `mount(container)` — inserta el canvas de la SDK y **la SDK escala** a esa caja. Legal en
  cualquier momento: mover un `<canvas>` en el DOM no pierde el contexto WebGL.
- `mount(canvasEl)` — ese elemento *es* la superficie. Sólo antes de `start()`: Emscripten
  ata el contexto GL al elemento al instanciar. El error lo dice con esas palabras.
- `parentEl.appendChild(sdk.canvasEl)` — colocación manual; entonces el escalado es del host.

`start()` exige `canvasEl.isConnected` y falla con un mensaje preciso si no. Desaparecen
`attachTo` y `canvasEl` como dos modos, y con ellos el bug de meter un canvas dentro de otro.

`start()` devuelve un *thenable* encadenable (el patrón de `PendingComponent79`), así que
`await sdk.start({...}).mount(box)` funciona. El contrato debe exigir que el rechazo salga
**también** por `on('error')`, para que un host que no hace `await` no se quede a ciegas.

**Restricción a escribir en el contrato:** SDL localiza el render target por `#canvas` →
un motor por documento. Hoy ya es cierto y no está dicho en ninguna parte.

## 2.4 `AssetSource`: valor o thunk

```ts
export type AssetData = Uint8Array | ArrayBuffer | Blob | string;
export type AssetSource = AssetData | (() => Promise<AssetData> | AssetData);
```

Un thunk sólo se invoca si el asset no está ya persistido. Se lleva por delante
`dataProvider`, `settingsProvider`, `romProvider`, `gameProvider` y la contradicción de
"`assets` es obligatorio pero mi pack ya está en OPFS": un thunk *es* un valor. `Blob`
entra porque celeste ya lo necesitaba por su cuenta y porque un `File` de OPFS no debería
materializarse en JS sólo para copiarlo al heap.

## 2.5 Tres cubos: `config`, `options`, `start`

| | quién lo escribe | cuándo | esquema |
| --- | --- | --- | --- |
| `sdk.config({...})` | el host, antes de arrancar | congelado con instancia viva | `manifest.config` |
| `instance.options({...})` | el jugador, en marcha | vivo, se escribe al momento | `manifest.options` **+** lo descubierto del pack |
| `sdk.start({...})` · `instance.restart({...})` | el host, por sesión | cada sesión | las propiedades `readOnly` de `instance.options()` |

Misma forma en los tres: un objeto. `.config()` se conoce sin cargar nada y cabe en un
esquema estático; `options()` funde lo vivo del motor con lo que expone el pack ya cargado
—Sonic 1 y Sonic 2 dan claves distintas— y sólo existe con el motor vivo.

```js
sdk.config({ devMenu: false, bgmVolume: 1 })   // arranque: todo
await instance.options({ devMenu: true })      // en marcha: sólo lo vivo
await instance.options({ spindash: 1 })        // y lo del pack, misma puerta
await instance.options()                       // getter: el mapa completo
```

**El getter es `manifest.options` resuelto en runtime**: cada propiedad con su JSON Schema
—vocabulario estándar `title`, `enum`, `minimum`, `readOnly`— más el valor actual, y las que
descubre del pack. Así cualquier generador de formularios lo pinta sin conocer el motor, y
`readOnly` marca lo que exige reiniciar para cambiar.

```js
{
  player:    { value: 0, type: 'integer', enum: [0,1,2,3], readOnly: true, source: 'game',
               title: 'Character', enumNames: ['SONIC','TAILS','KNUCKLES','SONIC & TAILS'] },
  spindash:  { value: 0, type: 'boolean', title: 'Spindash', source: 'game' },
  bgmVolume: { value: 0.8, type: 'number', minimum: 0, maximum: 1, source: 'engine' },
  vsync:     { value: true, type: 'boolean', readOnly: true, source: 'engine' },
}
```

Esto se lleva por delante **`startSchema()`** —era esta misma información en un método aparte,
y `player.enum` sale del GameConfig igual— y las filas con `label`/`values`, que decían lo mismo
con nombres inventados. El setter recibe **valores planos**, no la forma del getter: sería
ambiguo el día que una propiedad sea de tipo objeto.

**`config()` sin argumentos es el mismo getter, en la fábrica**, y ahí puede ser **síncrono**: no
hay motor al que preguntar, sólo `manifest.config` con lo que la cadena haya puesto encima
(`value` = lo puesto, o el `default` del manifest). Sirve para pintar una pantalla de
preferencias sin arrancar nada.

|  | `sdk.config()` | `instance.options()` |
| --- | --- | --- |
| coste | síncrono: manifest + cadena | asíncrono: cruza al worker |
| claves | sólo las del motor | las del motor **+** las del pack |
| `value` | lo que se usará al arrancar | lo que está en efecto ahora |
| `source` | no hace falta, todo es `engine` | `'engine'` \| `'game'` |

Una clave del motor sale en los dos, y las dos lecturas son correctas: `config()` dice con qué
arrancó, `options()` cómo está ahora. Sigue sin haber `instance.config()`.

**Dos listas en el manifest, sin anotaciones.** Estar en `manifest.options` **es** la
declaración de que la clave se puede cambiar en marcha; no hace falta marcar `live` en ningún
sitio. Medido en el motor:

| clave | `config` | `options` | por qué |
| --- | :-: | :-: | --- |
| `bgmVolume` · `sfxVolume` | ✓ | ✓ | `SetGameVolumes()` es llamable en cualquier momento |
| `screenWidth` | ✓ | ✓ | existe `SetScreenSize()`; realoja búferes, mejor fuera de partida |
| `devMenu` · `fastForwardSpeed` · `dimLimit` · `useHQModes` | ✓ | ✓ | globales que el motor lee cada frame |
| `language` | ✓ | ✓ | pero surte efecto en la escena siguiente: el texto se carga por escena |
| `vsync` | ✓ | | sólo se lee al crear el renderer — y en web el bucle es rAF, así que no hace nada |
| `engineDebugMode` · `startMenu` | ✓ | | los lee `Engine::Init` |
| `spindash` · `shieldType` · `stage` … | | descubiertas | del pack; ni siquiera son las mismas en Sonic 1 y Sonic 2 |

**Regla de `start()`/`restart()`:** el payload es *datos de sesión* (`slot`, `player`) **+** un
parcial de las claves de `options`, y nada más. Nunca `config` de arranque.

**Dos reglas de la bolsa de `options()`:**

1. Las filas llevan `source: 'engine' | 'game'`, para que una pantalla de ajustes genérica
   pueda agrupar sin cablear nada de RSDKv4.
2. Una clave del pack que colisione con una de `manifest.options` es **error al arrancar**, no
   sombra silenciosa.

### 2.5.1 El escenario es una opción más

`stages()`, `warp()` y `capabilities.stageSelect` **se caen del contrato**: el escenario actual
es una opción viva cuyo `enum` sale del pack, igual que `shieldType`.

```js
const { stage } = await instance.options()
// { value: 12, type: 'integer', enum: [0, 1, 2, …], title: 'Level', source: 'game',
//   enumNames: ['Presentation / TITLE SCREEN', …, 'Regular / GREEN HILL ZONE 1'] }

await instance.options({ stage: 12 })   // esto es el warp
```

- **Hay que aplanar**: RSDKv4 tiene cuatro listas × N escenarios
  ([WebDevMenu.cpp:21-33](../.tmp/rsdkv4-wasm-build/RSDKv4/WebDevMenu.cpp#L21-L33)) y un `enum` es
  plano. Prefijar la categoría en la etiqueta deja un solo selector en vez de dos; el valor es un
  índice opaco que el SDK traduce a `(lista, escena)`.
- **Escribirla no es como escribir las otras**: `spindash` cambia una bandera, `stage` recarga la
  escena y corta la música. Asumible aquí porque la metáfora de UI coincide — el *level select*
  del propio juego es exactamente una lista de la que eliges.
- El mapa lleva `enum`/`enumNames`/`title`: es lo que permite pintar la
  pantalla sin conocer el motor, y el selector de escenario es justo el caso que necesita
  `values`. Quien sólo quiera valores hace `Object.fromEntries(rows.map(r => [r.key, r.value]))`.

`EngineConfig` (el objeto entero) pasa a llamarse **`EngineSetup`**, liberando la palabra.

## 2.6 Eventos con nombre

```ts
export interface EngineEventMap {
  ready: void;                                   // arrancado; los getters ya responden
  start: { payload: unknown };                   // se abrió sesión
  progress: { key: string; loaded: number; total?: number };
  frame: { fps: number };
  error: { error: Error };
  exit: void;                                    // destroy() terminó
}

on<K extends keyof EngineEventMap>(type: K, handler: (e: EngineEventMap[K]) => void): this;
off<K extends keyof EngineEventMap>(type: K, handler: (e: EngineEventMap[K]) => void): this;
```

`progress` porque todo host con un pack de decenas de MB lo necesita y hoy no lo emite nadie.
`start` porque `start()` es reentrante y un host quiere enterarse de cada sesión, no sólo de
la primera.

## 2.7 El manifest adelgaza

Sigue siendo la mitad declarativa — **lo que un host sabe del motor sin cargarlo**, que es lo
que permite a `rom-manager` pintar el catálogo de diez motores sin instanciar un wasm. Debe
seguir alcanzable en estático: `Rsdkv4SDK.manifest`.

| campo | cambio |
| --- | --- |
| `assets[].mountPath` | **fuera**: filtra el VFS a quien no monta nada, y hoy además miente (`/data/Data.rsdk` cuando la ruta lleva namespace) |
| `assets[].validate` | **fuera**: validar es de cada motor (§2.12.1), y los CRC por título son de catálogo, no de manifest. `assets[]` queda en `{ key, required, accept?, description? }` |
| `options` | → **`config`**: ajustes de arranque, 1:1 con `sdk.config()` |
| `options` (nuevo) | las claves **vivas** que posee el motor, 1:1 con `instance.options()`. Estar aquí *es* la declaración de que se puede cambiar en marcha (§2.5) |
| ~~`start`~~ | **descartado**: la versión estática era pobre (`slot: 0-3`, `player: int`) y la útil la da `instance.options()`, donde `player` llega con su `enum` leído del pack. Consecuencia asumida: un host no puede pintar el formulario de "empezar partida" antes de arrancar — tampoco podía, le faltaban los personajes |
| `contractVersion` | **nuevo**: hoy un manifest no dice contra qué contrato se construyó |
| `capabilities` | se queda, definiendo cada bandera. `sram` = "las partidas sobreviven a un reload". **Nuevas**: `multiInstance` (por defecto `false`, §2.1), `saveSlots` y `savesOffline` (§2.8.2) |
| `artifacts`, `input`, `video` | sin cambios |

## 2.8 La instancia

Todo asíncrono, porque el motor tiene que poder vivir en un Worker: es la única forma de que
OPFS monte de verdad — hoy `wasmfs_create_opfs_backend()` se niega en el hilo principal sin
Asyncify/JSPI ([rsdkv4.sdk.ts:98-116](../src/rsdkv4.sdk.ts#L98-L116)). Con la instancia al
otro lado de un `postMessage`, todo es asíncrono; si la API nace síncrona, mudarse al Worker
es una versión mayor.

```ts
interface EngineInstance<Start = Record<string, unknown>> {
  // Sin start(): crear instancia es de la fábrica (§2.1).
  /** Reinicia la sesión en caliente con otros parámetros. Payload vacío = power cycle. */
  reset(payload?: Start): Hydrated<Start>;
  /** Pausa a nombre de `owner` (por defecto 'host'). Sólo quien pausó puede reanudar. */
  pause(owner?: string): Hydrated<Start>;
  resume(owner?: string): Hydrated<Start>;
  /** Getter: `manifest.options` resuelto en runtime — cada propiedad, su JSON Schema
   *  más `value` (§2.5). Setter: valores planos, sólo las que no sean `readOnly`. */
  options(): Promise<Record<string, ResolvedProperty>>;
  options(values: Record<string, number | boolean | string>): Hydrated<Start>;
  mount(container: HTMLElement): Hydrated<Start>;
  setInput(map: InputPreset | KeyMap): Hydrated<Start>;
  /** Sólo lo que el SDK escribió. Los assets son del host y no se tocan (§2.12). */
  purgeStorage?(): Promise<{ settings: boolean; saves: boolean }>;
  destroy(): Hydrated<Start>;

  // Con puerta en capabilities:
  saves?(): Promise<SaveSlot[]>;              // capabilities.saveSlots
  deleteSave?(id: string | number): Hydrated<Start>;
  saveState?(): Promise<Uint8Array>;          // capabilities.saveStates
  loadState?(data: Uint8Array): Hydrated<Start>;
  screenshot?(): Promise<Blob>;
}
```

### 2.8.0 `Hydrated`: encadenable sin que la instancia sea *thenable*

`instance` **nunca** tiene `then`. Lo thenable es lo que devuelve cada acción: una promesa
hidratada con los mismos nombres, donde cada uno espera a la anterior y devuelve otra
hidratada. Como resuelve en la instancia —que no es thenable— no hay *chaining cycle*, que es
lo que pasaría si `instance.then` existiera y `sdk.start()` la devolviera.

```ts
const CHAIN = ['pause', 'resume', 'reset', 'options', 'mount', 'deleteSave', 'warp', 'setInput', 'destroy'];
const GETTERS = new Set(['options', 'saves', 'storage', 'purgeStorage']);

function hydrate(p: Promise<EngineInstance>): Hydrated {
  for (const name of CHAIN) {
    p[name] = (...args) => {
      const isGetter = GETTERS.has(name) && args.length === 0;
      const next = p.then((i) => i[name](...args));      // métodos crudos, no hidratados
      return isGetter ? next : hydrate(next.then(() => p));
    };
  }
  return p as Hydrated;
}
```

```js
await instance.pause().reset({ slot: 2 })    // acciones: sigue hidratada
await instance.pause().saves()               // un getter cierra la cadena, no la continúa
```

Un rechazo aborta el resto de la cola y sale por el `await` **y** por `on('error')`: encadenar
no puede volver a esconder fallos.

`mount()` existe en los dos lados con retornos distintos, sin polimorfismo: `sdk.mount(target)`
devuelve la cadena de configuración; `instance.mount(container)` devuelve una hidratada.

### 2.8.1 Sin `instance.game`: todo sube a la API

No hay namespace por motor. Lo que haga falta se añade al contrato y se documenta; lo que no
generalice, se queda fuera. Mapa de lo que hoy es extensión de rsdkv4:

| hoy en la extensión | en el contrato | puerta |
| --- | --- | --- |
| `game.start(slot, player)` | `instance.reset(payload)` | — |
| `game.setOption(k, v)` · `game.options()` | `instance.options({ k: v })` · `options()` | — |
| `game.players()` | `(await instance.options()).player.enumNames` | — |
| `game.saveSlots()` · `deleteSave()` | `instance.saves()` · `deleteSave(id)` | `capabilities.saveSlots` |
| `game.type()` | **nada** — se descarta | — |
| `devMenu.getStageList()` · `loadStage()` | `instance.options()` · `options({ stage })` (§2.5.1) | — |

**`game.type()` se descarta sin sustituto.** Lo generalicé a un `info()` y no le he encontrado
consumidor: el host eligió el fichero, así que sabe qué cargó. Craft lo resuelve además **antes
y mejor**, con el CRC32 del fichero soltado ([game.service.js:96-110](../src/craft/services/game.service.js#L96-L110)),
sin arrancar nada. Queda el caso teórico de motores con cientos de títulos (fbneo) donde un host
genérico querría el nombre de lo que corre — pero eso es catálogo, y el catálogo es de
`rom-manager`. Fuera hasta que haya un caso concreto.

### 2.8.2 `sdk.saves()`: leer partidas sin arrancar

```js
const slots = await sdk.saves()   // sin wasm, sin arrancar
```

La objeción obvia es que duplica el formato de `SData.bin` en JS. Es floja, porque **la
duplicación ya existe**: está en C++ (`web_get_save_slots`) y en JS
([game.service.js:65-94](../src/craft/services/game.service.js#L65-L94)). La pregunta no es si
duplicar, sino dónde vive la copia JS — en cada lanzador, como ahora, o una vez en el SDK. Y el
formato es minúsculo: `Int32Array`, ocho enteros por ranura, quince líneas.

Con puerta en `capabilities.savesOffline`, y con un test que cierre la deriva: arrancar, escribir
una partida, comparar `sdk.saves()` contra `instance.saves()` fila a fila.

**Lo que no sube a la fábrica** es `options()`: sale del `Data.rsdk`, y parsear un pack de 40 MB
en JS para ahorrarse un arranque es peor negocio que arrancar.

**`options()` evita meter vocabulario de Sonic en el contrato**: `player` llega con
`enum: [0,1,2,3]` y `enumNames: ['SONIC','TAILS','KNUCKLES','SONIC & TAILS']` leídos del
GameConfig, así que un host genérico pinta el selector de personaje sin saber qué motor tiene
delante — y sin que el contrato mencione personajes.

**`saves()`** paga el precio de no tener extensión: filas con lo común (`id`, `empty`,
`label`) y lo específico en `meta` (vidas, esmeraldas, zona). Un host genérico enseña
`label`; uno que sepa que es rsdkv4 lee `meta`. Menos expresivo que un `saveSlots()` tipado,
y es el precio correcto: la alternativa era un namespace que nadie puede consumir sin
ramificar por motor.

Con esto **`Rsdkv4Instance` desaparece como tipo**: la instancia *es* `EngineInstance` con
los genéricos cerrados. Cero superficie propia.

`pause(owner)` sube al contrato tal cual: rsdkv4 ya lo necesitó (overlay de pausa, pantalla
de inicio y host pausándose entre sí) y cualquier host con overlays tiene el mismo problema.

`purgeStorage()` sólo borra lo que el SDK escribió. **Hoy es un bug de diseño**: rsdkv4 borra
`Data.rsdk` ([rsdkv4.sdk.ts:719-724](../src/rsdkv4.sdk.ts#L719-L724)), o sea el pack del
jugador, que no es suyo (§2.12). Y mGBA copia la forma `{data, settings}` sin que signifique
nada para un motor de `rom` + `bios`.

`.on()` se copia a la instancia igual que `.config()`: los handlers de la fábrica entran en
cada instancia nueva, y lo que la instancia añada o quite no afecta a la fábrica. Son
**síncronos**, porque registrar un listener es local — no cruza al worker, sólo decide a quién
reenvía el SDK los eventos que le llegan.

## 2.9 `load()` protegido: la cadena se escribe una vez

`load(setup)` deja de ser API pública y pasa a ser **lo único que implementa cada motor**.
La cadena vive en la clase base del contrato:

```ts
export abstract class EngineBuilder<Config, Start> {
  /** El objeto plano también entra por aquí: new Rsdkv4SDK(setupGuardado) */
  constructor(setup: EngineSetup<Config> = {}) { this.#setup = setup }

  /** Lo único que implementa cada motor. El host nunca lo ve. */
  protected abstract load(setup: EngineSetup<Config>): Promise<EngineInstance<Start>>;

  // assets() · config() · storage() · on() · mount() · start() viven aquí
}

export class Rsdkv4SDK extends EngineBuilder<Rsdkv4Config, Rsdkv4Start> {
  static manifest = manifest;
  protected load(setup) { /* lo que hoy es load(config) */ }
}
```

Por qué la base y no diez implementaciones: las reglas de fase (§2.2), las tres formas de
`mount()` (§2.3), el *thenable* encadenable y el `isConnected` se escriben **una vez**. Diez
clases propias son diez juegos de bugs y diez derivas — exactamente la situación de la que
venimos, con tres nombres distintos para el mismo `dataProvider`.

El constructor acepta el `EngineSetup` plano porque la cadena no es serializable y hay tres
casos que lo necesitan: configuración en JSON, tests de tabla, y restaurar la última sesión
del jugador desde `localStorage`.

## 2.9.1 `boot()`: motor vivo, sin sesión

`sdk.boot()` devuelve la instancia con el motor arrancado y **sin partida**: pantalla neutra y
`saves()` ya legible (el `saveRAM` se carga en `Engine::Init`, antes de nada). Es el estado en el
que un lanzador quiere pintar sus tarjetas.

**Necesita un cambio en el motor.** `InitFirstStage()` ([Scene.cpp:83-99](../.tmp/rsdkv4-wasm-build/RSDKv4/Scene.cpp#L83-L99))
se ejecuta siempre al arrancar y deja el motor cargando la presentación 0 — splash y título,
con su música. No hay estado inerte al que llegar, y pausar desde JS es una carrera contra el
primer frame: se verían uno o dos frames de splash. Hace falta un `web_boot_idle()` que deje
`stageMode` en pausa **antes** de cargar, no un `pause()` disparado desde fuera.

```js
const instance = await sdk.boot()                      // neutra, muda, saves() legible
await sdk.start()                                      // por defecto, o el menú si startMenu:'native'
await sdk.start({ slot: 0, player: 1 })                // = boot() + restart(payload)
await instance.restart({ slot: 2 })                    // reabrir
```

## 2.10 Lo que le queda a rsdkv4 como extensión

**Nada.** `instance.game` y `instance.devMenu` no se exponen: metían ruido y obligaban a
cualquier host a ramificar por motor. Todo lo que hacía falta subió a la API con puerta en
`capabilities` (§2.8.1), y lo que no generalice simplemente no se expone.

La consecuencia de diseño, que conviene tener presente al migrar los otros nueve motores: el
contrato crece cada vez que un motor necesita algo nuevo. Es deliberado — un contrato que
crece despacio y en público es preferible a diez namespaces privados que nadie puede
consumir — pero exige disciplina en la puerta de entrada: **si no lo puede usar un host
genérico, no entra**.

## 2.12 Ciclo de vida de los assets

### Cómo es hoy, en los ocho motores

| motor | cómo recibe los bytes | dónde viven en reposo |
| --- | --- | --- |
| mGBA · snes9x · geolith | `_malloc` + `HEAPU8.set` → puntero y longitud | OPFS, leído desde JS |
| rsdkv4 · fbneo · blastem | `FS.writeFile` / `createDataFile`; el motor abre por ruta | OPFS (rsdkv4), nada los otros dos |
| jgenesis | `channel.request_open_rom_bytes()`; copia el glue de wasm-bindgen | OPFS |
| celeste | el SDK escribe en OPFS y el runtime .NET lee de ahí | OPFS |

**Ninguno lee de OPFS dentro del wasm.** Los bytes acaban siempre copiados. rsdkv4 es el único
que lo intenta y está inerte: `wasmfs_create_opfs_backend()` levanta un worker proxy de forma
síncrona y aborta en el hilo principal sin Asyncify/JSPI.

### El desperdicio, medido

`Reader.cpp` lee el pack con `byte fileBuffer[0x2000]` — 8 KB, `fread` + seek
([Reader.hpp:79](../.tmp/rsdkv4-wasm-build/RSDKv4/Reader.hpp#L79)). El motor **nunca quiere el
`Data.rsdk` entero**. Hoy pagamos `arrayBuffer()` (40 MB en JS) + `FS.writeFile` (40 MB en el
heap) de un `TOTAL_MEMORY=268435456` **fijo** — el parche de WASMFS se comió el
`ALLOW_MEMORY_GROWTH` ([build.sh:48](../scripts/build.sh#L48)) — para alimentar un lector de
8 KB. Con el fichero en un VFS sobre OPFS, esos 40 MB no entran en memoria en ningún sitio.

### `AssetSpec`, mínimo

```ts
interface AssetSpec {
  key: string;
  required: boolean;
  accept?: string[];        // para el picker del host
  description?: string;     // texto para ese picker
}
```

Con `mountPath` y `validate` fuera (ver más abajo), nada más. El manifest describe **qué**
necesita el motor y cómo pedírselo al jugador; ni dónde vive ni cómo llega.

### `missingAssets()`, y sólo eso

```js
sdk.missingAssets()   // ['data'] — síncrono: mira la cadena, no el disco
```

Valida qué claves `required` no se han pasado a `.assets()`. **No existe `missingStorage()`**:
si el SDK no dicta el layout de la biblioteca, no sabe dónde mirar — y el host sí, porque es
suya. Craft ya lo hace ([game.service.js:41-59](../src/craft/services/game.service.js#L41-L59)),
y bajo este reparto eso deja de ser duplicación: es su trabajo.

### Quién posee qué

- **`.assets()` = entradas del jugador, propiedad del host.** El SDK **nunca escribe assets, ni
  crea su ubicación**. Guardarlos, nombrarlos, validarlos por CRC, deduplicar y saber si ya
  están es trabajo del lanzador — craft ya lo hace, y hacerlo dos veces sólo puede divergir.
- **`.storage()` = estado propio del SDK**: `settings.ini` y `SData.bin`. Lee y escribe.

El SDK es un runtime, no un gestor de biblioteca. El host guarda el fichero donde quiera y le
**presta la puerta**:

```js
await miBiblioteca.escribir(`${id}.rsdk`, file)          // el host, con su layout
const handle = await miBiblioteca.handle(`${id}.rsdk`)
sdk.assets({ data: handle }).storage({ namespace: `saves/${id}` })
```

Consecuencia de que el SDK no dicte layout: **no hay `assetTarget()` ni `missingStorage()`**
(para dar un destino habría que crearlo, o sea escribir), y `AssetSpec.supply` sobra — sólo
queda un canal, `.assets()`. Tampoco hay `storage-required`: rsdkv4 puede correr con un handle
y sin `storage()`, simplemente sin guardar partidas.

**Precio técnico:** WASMFS monta **directorios por ruta**, no ficheros por handle. Para leer a
trozos de un handle prestado hace falta un backend propio en C++ sobre
`createSyncAccessHandle()`. Es trabajo del motor, no del contrato, pero es más que montar un
directorio: si no se hace, un handle degrada a copia y se pierde el copia-cero.

### Reglas para el contrato

1. **El contrato declara el origen, nunca el mecanismo.** Confirma quitar `mountPath` del
   manifest: son cuatro mecanismos distintos y ninguno es asunto del host.
2. **La API nunca nombra OPFS.** El host entrega bytes o un handle; dónde vive el fichero es
   asunto suyo:

   ```ts
   export type AssetSource =
     | AssetData                    // bytes: el SDK los sube al heap
     | FileSystemFileHandle         // préstamo: el SDK lee a demanda si puede
     | (() => Promise<AssetData | FileSystemFileHandle>)
   ```

   Un handle de OPFS se lee con acceso síncrono en el worker (8 KB cada vez, el pack no entra en
   memoria); uno de `showOpenFilePicker()` sobre disco no tiene acceso síncrono y obliga a
   copiar. Eso es asunto interno del SDK.
3. **El host guarda, el SDK lee.** La cadena `'Data.rsdk'` deja de estar escrita en dos repos —
   hoy lo está, en [opfs.service.js](../src/craft/services/opfs.service.js) y en
   [rsdkv4.sdk.ts:515](../src/rsdkv4.sdk.ts#L515), sostenida por un comentario— porque el SDK ya
   no busca ficheros por nombre: recibe el que le den.
4. **Cambiar un asset rearranca el motor**, y debe ser observable: `exit` seguido de `ready`.
   `sdk.assets({...}).start({...})` y `.restart({...})` son válidos; lo que no vale es que dos
   llamadas iguales cuesten 5 ms y 2 s sin ninguna señal.
5. **Si el host entrega un `Blob` o un stream, la SDK no debe materializarlo entero en JS.**
   Calidad de implementación, pero escrita es revisable — y celeste ya lo hace
   ([celeste.sdk.ts:1394](/Users/joshua/dev/wasm-gaming/celeste-wasm/src/celeste.sdk.ts#L1394)).

### Coherencia entre JS y el wasm sobre el mismo OPFS

`createSyncAccessHandle()` toma un **candado exclusivo** (modo `readwrite`, el de por defecto).
Mientras el motor tiene abierto un fichero por esa vía, un `createWritable()` desde JS sobre el
mismo fichero falla con `NoModificationAllowedError`. No hay escritura que se pierda en
silencio: hay excepción.

| situación | qué pasa |
| --- | --- |
| JS escribe un fichero que el motor tiene abierto | **error** por el candado |
| JS crea un fichero que el motor aún no ha abierto | debería verlo al hacer `fopen` |
| JS reescribe un fichero cerrado, el motor lo abre después | contenido nuevo, correcto |
| dos escritores a la vez sobre el mismo fichero | indefinido |

Además, RSDKv4 tiene su búfer de 8 KB: aunque el candado no saltara, un cambio a mitad de
lectura daría trozos viejos y nuevos mezclados. La coherencia del FS no salva del búfer de la
aplicación.

**Consecuencias:**

1. **El espejo de partidas actual y el montaje OPFS son incompatibles, no redundantes.** Hoy el
   SDK escribe `SData.bin` desde JS cada 10 s ([rsdkv4.sdk.ts:678-680](../src/rsdkv4.sdk.ts#L678-L680));
   con el motor montando ese directorio en un worker, esas escrituras chocan con su candado.
   Hay que quitarlas, no sólo dejarlas de usar.
2. **`.storage()` es exclusivo del SDK**, y ahora por razón técnica: es donde el motor escribe
   con candados.
3. **"Instalar antes de jugar" es regla del contrato**: reemplazar un pack en uso exige
   `destroy()` → escribir → `start()`. Instalar otro juego mientras juegas no da problema.

*Sin verificar:* cuánto cachea WASMFS las entradas de directorio — si un fichero creado desde JS
tras el montaje aparece en el `fopen` siguiente. Va a la prueba de humo (Parte 3).

### 2.12.1 Comprobar el almacenamiento en `start()`

`start()` valida **antes de instanciar el wasm** —levantar el worker es barato, descargar los
megas no— y rechaza con error tipado.

| comprobación | qué detecta |
| --- | --- |
| `navigator.storage?.getDirectory` | navegador sin OPFS, modo privado |
| `crossOriginIsolated` | faltan COOP/COEP → sin hilos |
| `createSyncAccessHandle()` sobre un fichero sonda | **la única definitiva** |
| `navigator.storage.estimate()` | no cabe el pack |

**Sin checksum en el contrato.** Validar el pack es de cada motor y rsdkv4 ya lo hace:
`CheckRSDKFile()` lee la firma `RSDKvB` antes de nada
([Reader.cpp:25-48](../.tmp/rsdkv4-wasm-build/RSDKv4/Reader.cpp#L25-L48)) y `LoadGameConfig()`
es la condición de todo el arranque ([RetroEngine.cpp:329](../.tmp/rsdkv4-wasm-build/RSDKv4/RetroEngine.cpp#L329)):
un pack truncado no inicializa nada. Luego `AssetSpec.validate` sale del manifest — y de todas
formas no podía expresar lo que hace falta, porque los CRC por título (Sonic 1 vs Sonic 2, hoy
cableados en [game.service.js:16-25](../src/craft/services/game.service.js#L16-L25)) son dato de
catálogo, no de motor: viven en el host.

**Pero hay que arreglar el reporte.** Hoy, si `LoadGameConfig` falla, `web_engine_ready()` nunca
devuelve true, `waitForEngine()` agota sus 4 s y el SDK **emite `ready` igual**
([rsdkv4.sdk.ts:672-682](../src/rsdkv4.sdk.ts#L672-L682)): el host recibe "listo" sobre un motor
muerto. Sin ready → `error` con `asset-invalid`, y entonces la especificación no necesita decir
nada más.

**Si es obligatorio se deriva de lo que pidió el host**, sin bandera nueva en el manifest:

| lo que pasó el host | ¿OPFS obligatorio? |
| --- | --- |
| `assets({ data: { opfs: '…' } })` | sí — sin OPFS no hay cómo leer el pack |
| `assets({ data: bytes })` | no |
| `storage({ namespace })` | sólo partidas: sin OPFS, degradación |
| ninguno | no se comprueba nada |

Para el caso intermedio, que elija el host: `storage({ namespace, required: true })` falla al
arrancar; con `required: false` (por defecto) degrada y se consulta con
`await instance.storage()` → `{ namespace, persistent }`, que sustituye al `persistent` suelto
de hoy.

```ts
class EngineStartError extends Error {
  code: 'storage-unavailable' | 'not-isolated' | 'storage-locked' | 'quota-exceeded'
      | 'asset-missing'       // un required no se pasó a .assets()
      | 'asset-invalid'       // el motor rechazó el fichero (firma, GameConfig)
      | 'unsupported-browser';
}
```

`storage-locked` (otra pestaña del mismo origen tiene el candado) es el que más se olvida y el
único que el jugador arregla en dos segundos si se lo dices. Hoy nada de esto existe: la SDK
avisa por `console.warn` y sigue ([rsdkv4.sdk.ts:142-146](../src/rsdkv4.sdk.ts#L142-L146)), así
que el host no se entera de que va a jugar sin guardar hasta que el jugador pierde la partida.

## Parte 3 — Reescritura del lado wasm (rsdkv4)

Prerrequisito de casi todo lo anterior: **el motor tiene que correr en un worker**. Es lo que
habilita OPFS de verdad y lo que justifica que la API nazca asíncrona (§2.8).

Flags actuales ([build.sh:48](../scripts/build.sh#L48)): `WASMFS`, `FORCE_FILESYSTEM`,
`MODULARIZE`, `EXPORT_ES6`, `INVOKE_RUN=0`, `TOTAL_MEMORY=256MB`. **Sin hilos.** El salto:

1. `-pthread` y `-sPROXY_TO_PTHREAD`: `main()` deja el hilo del navegador y
   `wasmfs_create_opfs_backend()` ya puede levantar su proxy.
2. `-sOFFSCREENCANVAS_SUPPORT=1` + `transferControlToOffscreen()`. Sin esto cada llamada GL se
   proxya al hilo principal y el juego va a pedales. Safari lo soporta desde 16.4.
3. Recuperar `ALLOW_MEMORY_GROWTH`: con el pack fuera del heap ya no hay que dimensionar para
   el peor caso.
4. Aislamiento cross-origin: ya resuelto (`coi.js`, `_headers`).

**Lo que se borra del SDK cuando esto entra:** el espejo de `SData.bin` completo —
`restoreSaveData`, `persistSaveData`, el temporizador de 10 s y el volcado en `destroy()`, unas
60 líneas ([rsdkv4.sdk.ts:221-260](../src/rsdkv4.sdk.ts#L221-L260))—, `web_opfs_supported()` y
la rama de "avisa y cae a memoria", el `FS.writeFile` de 40 MB, y `persistent` como incógnita
que el host tiene que consultar.

**Refuerza `mount()`:** en un worker, `mount(canvasEl)` implica `transferControlToOffscreen()`,
y esa transferencia es **irreversible** — ese elemento no vuelve a servir para 2D ni para otra
instancia. La regla "sólo antes de `start()`" deja de ser convención y pasa a ser física.

### Prueba de humo

Dos cosas que medir con el juego en marcha, no con una demo, antes de dar por bueno el worker:

**Audio.** El callback de SDL (`want.callback = ProcessAudioPlayback`,
[Audio.cpp:64](../.tmp/rsdkv4-wasm-build/RSDKv4/Audio.cpp#L64)) descodifica el Ogg de la música
**leyendo del pack** ([Audio.cpp:391-398](../.tmp/rsdkv4-wasm-build/RSDKv4/Audio.cpp#L391-L398)),
y los sync access handles de OPFS sólo existen en el worker. Si SDL invoca el callback en el hilo
principal, ese `fread` no se resuelve ahí. Si aparece, la salida limpia es pre-bufferizar la
música en el hilo del motor y dejar el callback como simple copia de un anillo — cambio en
`Audio.cpp`, no en el SDK. No afecta a `boot()` ni al lanzador: sólo a la partida con OPFS
montado.

**Input.** Emscripten reenvía los eventos DOM del hilo principal a la cola del pthread: un salto
por evento, hay que ver si se nota. Lo que sí cambia seguro es la localización del canvas — con
OffscreenCanvas transferido, el `document.querySelector('#canvas')` de SDL no existe en el worker
y hay que apuntarle al canvas transferido, lo que toca el `mount()` de §2.3.

## Respuestas a §15

**P1 · `capabilities.saves` como escala.** Respondido por otro lado: *el payload de `sdk.saves()`
e `instance.saves()` depende de cada juego*. Eso no contesta escala-vs-booleanos, lo refuerza —
si las filas las declara el contenido cargado, la capacidad no puede describir *qué* se lee, sólo
**dónde** (`false | 'engine' | 'storage'`), que es exactamente la escala. Y obliga a algo que la
spec todavía no dice: el contrato fija un núcleo mínimo de fila (índice/ranura y "vacía o no") y
el resto es del motor, como pasa con `options()`. Hoy [rsdkv4.sdk.ts:281](../src/rsdkv4.sdk.ts#L281)
(`RsdkSaveSlot`) ya es una fila específica de RSDKv4 — es el caso de prueba.

**P4 · Eventos `pause` / `resume`.** *Cada motor lo maneja como crea conveniente.* Es decir:
entran en el catálogo con forma fija, pero **no son obligatorios**. Consecuencia para el host:
no puede construir su UI asumiendo que llegan; quien los emita, que los emita así.

**P5 · `video` frente a `config`.** Opción (b): la geometría vive en `.config`, no en un campo
`video` aparte. Funciona sin perder el caso del lanzador precisamente porque `config` es un JSON
Schema: `config.properties.baseWidth.default` da la geometría nativa sin instanciar nada, y
`readOnly: true` marca los motores que no la cambian en caliente. Queda un fleco: `aspect` sale
de `baseWidth`/`baseHeight` salvo píxel no cuadrado — en rsdkv4 los 424×240 ya son 16:9 real,
así que aquí no se nota.

**P10 · Payload acumulativo. Confirmado:** `restart({ slot: 3 })` ≡
`restart({ ...previousOptions, slot: 3 })`. Fleco a cerrar en la spec: si el host escribe en
caliente con `instance.options({ stage })`, ese valor **también** forma parte de
`previousOptions` — si no, un `restart({ slot: 3 })` revertiría el cambio en silencio, que es
justo lo que P10(a) evita.

## Hilos: qué gana y qué cuesta

RSDKv4 es monohilo, así que `-sPROXY_TO_PTHREAD` no reparte trabajo: lo **cambia de sitio**. El
frame rate del motor no mejora por sí solo.

- **Se gana** OPFS de verdad (los sync access handles sólo existen en un worker) y un hilo
  principal que deja de bloquearse: hoy el `FS.writeFile` de 40 MB congela la página.
- **Se puede perder**, y es lo importante: sin `transferControlToOffscreen()` cada llamada GL se
  proxya al hilo principal, una ida y vuelta por llamada — **peor que hoy**. Los pasos 1 y 2 del
  plan (`-pthread` y OffscreenCanvas) no son secuenciales, son el mismo paso.
- **Input:** un salto por evento. Latencia, no throughput; medible.
- **Memoria:** con `-pthread` el heap es `SharedArrayBuffer` y `ALLOW_MEMORY_GROWTH` sigue
  soportado, pero cada crecimiento es más caro (todos los hilos re-derivan sus vistas). Con el
  pack fuera del heap debería ser raro; si no lo es, dimensionar y no crecer.
- **Audio:** el riesgo real, ya descrito en la Parte 3.

Resumen: la ganancia es arquitectónica, no de FPS, y sólo es neutra en FPS si OffscreenCanvas
entra a la vez.

# Extensión · 2026-08-14 — Revisión de `EngineSDK`/`EnginePlay` (engine-specs 7aa8aed)

Layer B reescrita como dos clases abstractas (`EngineSDK` fábrica + `EnginePlay` motor vivo),
`PlayPromise<Play> = Promise<Play> & Play`, y fuera `EngineConfig`/`EngineInstance`/`AssetData`/
`PersistMode`. Revisado **compilando**, no leyendo: un motor de conformidad rsdkv4 completo
(clase `Rsdkv4Play` con extensión propia `players()`, `Rsdkv4SDK` con `static manifest`, la línea
`EngineSDKClass` de §13, y uso desde el host con cadena) contra el `dist` de ese commit.

## Lo que funciona

La cadena **aguanta a nivel de tipos**, que era la pieza frágil del plan:
`play.pause('menu').options({ player: 2 }).resume('menu')` encadena,
`.pause('menu').saves()` cierra, y `players()` —método sólo de rsdkv4— sobrevive a la cadena por
polimorfismo de `this`. Cero errores una vez arreglado el punto 1.

## 1 · Los métodos capados no compilan como dicen que compilan — bloqueante

`abstract saves?(): …` no hace lo que promete el doc ("existen si y sólo si `capabilities` lo
dice"). TypeScript **exige implementar los miembros abstractos opcionales**:

```
TS2654: Non-abstract class 'Rsdkv4Play' is missing implementations for the following
members of 'EnginePlay': 'saveState', 'loadState', 'screenshot'.
```

O sea: cada motor tiene que declarar las cinco capacidades, incluidas las que no tiene. Doce
motores × cinco miembros, y `if (play.saveState)` deja de coincidir con el manifest.

Arreglo verificado — **fusión de declaraciones**: una `interface EnginePlay` del mismo nombre
con las cinco firmas opcionales, junto a la clase abstracta. Con eso el fichero de conformidad
compila entero, `if (play.saves)` sigue estrechando, y el motor que sí las implementa las tiene
no-opcionales. (La otra forma, `saves?: () => Promise<…>` como propiedad, también compila pero
obliga a escribirlas como *arrow properties*: un método normal da `TS2425`.)

## 2 · El orden de los genéricos está cruzado

`EngineSDK<Config, Options, Play>` frente a `EnginePlay<Options, Config>`. Escribirlos igual —el
error natural— sí se detecta, pero con ocho niveles de mensaje sobre `deleteSave`, `then` y
`onfulfilled` que no mencionan nunca el cruce; y sólo se detecta porque los dos tipos difieren
estructuralmente. Mismo orden en las dos clases y desaparece.

## 3 · El payload de `start` llega como `unknown`

`EngineEventMap.start: { payload: unknown }`, y `on`/`off` no son genéricos sobre `Options`:

```ts
play.on('start', (e) => { const p: Rsdkv4Options = e.payload })
// TS2322: Type 'unknown' is not assignable to …
```

El único evento que lleva el payload pierde justo el tipado que motiva la reescritura.
`EngineEventMap<Options>` hilado por `on`/`off` en las dos clases.

## 4 · Todo abstracto: hoy la clase base no reutiliza nada

`boot()` y `start()` también son abstractos, y son precisamente los que §13 quiere escritos una
sola vez. Un motor que migre hoy escribe la cadena entera y la tira en F3. Además, mientras
`boot()` sea abstracto nada obliga a llamar a `create()`, así que "el motor sólo aporta
`create()`" no es comprobable. **Consecuencia para el plan: F3 antes que rsdkv4**, no rsdkv4
primero.

## 5 · La capa A no se movió con la B

`engine.ts` documenta `manifest.config`, `capabilities.saves` y `capabilities.screenshots`;
`manifest.ts` sigue declarando `options`, `sram`, `coreSelectable`, `mountPath`, `validate` y
ningún `contractVersion`. El JSON Schema, el validador Zod y los 32 tests siguen siendo 0.1.1, y
la referencia publicada describe un manifest que no existe. PLAN-1.0 ponía F1 (capa A) antes que
F2; fue al revés.

Menor: `EngineSetup.on` es `Partial<EngineEventHandlers>` en el código y `Partial<EngineEventMap>`
en API-fullexample §3.6 — manda el código. Y `demo/demo.sdk.js` sigue siendo `{ manifest, load }`,
así que la única implementación de referencia del repo contradice la capa B (eso es F4).
