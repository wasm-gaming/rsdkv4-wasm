# Standalone package and a WASMFS namespace owned by the engine

2026-11-12 · Phase 0 of the cross-repo plan
([wasm-gaming.github.io · homogenize-engine-integration](https://github.com/wasm-gaming/wasm-gaming.github.io/blob/claude/happy-hypatia-jot71i/SESSIONS/2026-11-12_00h00.homogenize-engine-integration.session.md),
[play.germade · launcher-consumes-engine-packages](https://github.com/jgermade/play.germade/blob/claude/happy-hypatia-jot71i/SESSIONS/2026-11-12_00h00.launcher-consumes-engine-packages.session.md)).

**Status:** plan, pending approval.

rsdkv4 is the reference engine for the rest of the ecosystem, and the first one the
play.germade launcher will consume. Before any other engine is migrated, this repo has to meet
the three rules the owner set on 2026-11-12:

1. **Every repository works on its own.**
2. **`@wasm-gaming/engine-specs` is the one exception**: a regular dependency of every engine.
3. **Every engine has its own namespace in WASMFS.**

## Where it is today (verified in `2dbe5a2`, v0.2.1)

| rule | today | gap |
| --- | --- | --- |
| standalone | built `dist/rsdkv4/rsdkv4.sdk.js` and `rsdkv4.options.js` keep a bare `import … from '@wasm-gaming/engine-specs'`; `build-specs` copies the runtime to `dist/engine-specs.js`, **outside** `files: ["dist/rsdkv4/"]`, so the npm tarball does not even ship it | a host needs a bundler or an import map (craft and vanilla carry one) |
| contract dep | `peerDependencies` + `devDependencies` `^0.3.2` | should be `dependencies` |
| WASMFS namespace | `/data` = OPFS root; work dir = `/data/<namespace>`, default `default` — the same `default/` snes9x, mGBA and geolith fall back to. The `rsdkv4/` prefix exists only by host convention (craft passes `rsdkv4/${gameId}`) | the engine must own `rsdkv4/` |
| safety | `normalizeStorageNamespace` keeps `[A-Za-z0-9._-]`, so `..` and `.` survive: `namespace: '../x'` → `/data/../x` | **bug** — escapes the work root |
| docs | README "Contract surface" still documents `import { manifest, load }` and `storageNamespace` | stale since the 1.0 migration |

## Changes

### A · WASMFS / OPFS layout owned by the engine

```
OPFS root (= WASMFS /data)
└── rsdkv4/              ← Rsdkv4SDK.id, added by the SDK, not by the host
    └── <namespace>/     ← host's choice, default "default"
        ├── Data.rsdk
        ├── settings.ini
        └── SData.bin
```

1. New `storagePath(engineId, namespace)` in `src/rsdkv4.sdk.ts`, written as a free function with
   no rsdkv4 specifics so it can move verbatim to engine-specs later:
   - splits on `/`, trims, drops empty, **drops `.` and `..`**, replaces anything outside
     `[A-Za-z0-9._-]` with `_`;
   - empty result → `default`;
   - returns `${engineId}/${cleaned}`.
2. `#workDir = /data/${storagePath('rsdkv4', ns)}`; `opfsNamespaceDir()` walks the same path, so
   the SData.bin mirror, the persisted-pack check and the work dir keep agreeing.
3. **Compatibility with today's hosts:** a namespace that already starts with `rsdkv4/` has that
   segment stripped once (craft's `rsdkv4/Sonic1` still resolves to `rsdkv4/Sonic1`, not
   `rsdkv4/rsdkv4/Sonic1`), with a one-time `console.warn` saying to pass `Sonic1`.
4. **Legacy `default/`:** on boot with the default namespace, if `rsdkv4/default/` has no
   `Data.rsdk`/`SData.bin` and a top-level `default/` does, **copy** (not move) just those three
   rsdkv4 files across. The top-level folder is left alone: other engines use `default/` too.
5. `Rsdkv4Play` gains `get storagePath(): string` (`'rsdkv4/sonic-1'`), the OPFS-relative path a
   host uses to pre-stage files. `namespace` keeps returning the host-side, cleaned value.
6. `storage.namespace` description in `RSDKV4_SPEC` updated to say it is relative to `rsdkv4/`.

### B · Self-contained ESM

1. `build-specs` copies `engine-specs.js` to **`dist/rsdkv4/engine-specs.js`** (inside `files`).
2. New `scripts/localize-specs.mjs`, run after `tsc`: rewrites `from '@wasm-gaming/engine-specs'`
   to `from './engine-specs.js'` in `dist/rsdkv4/*.js` (the `.d.ts` keep the bare specifier: types
   come from the dependency). engine-specs 0.3.2's runtime has zero imports, so the copy is closed.
3. Drop `dist/engine-specs.js` and the `@wasm-gaming/engine-specs` entry from the import maps of
   `src/craft/index.html` and `src/vanilla/index.html`.
4. A plain static page doing `import Rsdkv4SDK from '/rsdkv4/rsdkv4.sdk.js'` with no import map
   must load — added as a check (below).

Trade-off: a bundler-based host that also imports engine-specs gets a second copy of the runtime
(~a few KB). The contract is structural, so two copies interoperate; correctness does not depend
on one shared instance.

### C · package.json

- `@wasm-gaming/engine-specs` `^0.3.2` → `dependencies`; remove `peerDependencies` and its comment.
- Version **0.3.0**: the storage layout change is visible to hosts that read OPFS directly.

### D · Hosts in this repo

- craft: `.storage({ namespace: gameId })`; `opfs.service.js` keeps `LIBRARY_DIR = 'rsdkv4'`, which
  now matches the engine instead of mirroring a convention. Comments updated.
- vanilla still uses the pre-1.0 `storageNamespace` API; out of scope (it is not in `make up`), noted.

### E · README

- "Contract surface": the chained class API (`new Rsdkv4SDK().assets().storage().mount().start()`).
- "Filesystem": the `rsdkv4/<namespace>/` layout, the compatibility rule, `play.storagePath`.
- "Install": one dependency, no import map needed.

## Extension · 2026-11-13 — Fix: the v0.3.0 release archive shipped an unlocalized SDK

Found when play.germade consumed the published release: `rsdkv4.tar.gz` (v0.3.0) has
`rsdkv4/rsdkv4.sdk.js` importing the bare `@wasm-gaming/engine-specs`, which no static server
resolves. The npm package is fine (packed before). Cause: CI runs `make build-sdk` (tsc, then
`build-specs` rewrites the import to `./engine-specs.js`) and later `make demo`, whose `build-demo`
depends on `build-lib` — a second `tsc` emit over `dist/rsdkv4/` that undoes the rewrite.

Fix:
- `build-lib` itself copies `engine-specs.js` and localizes the imports right after `tsc`, so every
  emit of the SDK — whoever triggers it — comes out self-contained; `build-specs` stays as an alias.
- The release's "Pack the site" step asserts the packed SDK imports `./engine-specs.js` and that the
  file is beside it, so a broken archive fails the release instead of shipping.
- Release **patch** → 0.3.1; play.germade pins 0.3.1.
