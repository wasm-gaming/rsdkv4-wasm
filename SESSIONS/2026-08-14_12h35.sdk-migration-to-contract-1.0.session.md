# Migrar la SDK de rsdkv4 al contrato 1.0

2026-08-14 · continúa [2026-08-13_01h49.engine-specs-refinement.md](2026-08-13_01h49.engine-specs-refinement.md)

rsdkv4 es el motor piloto de `PLAN-1.0.md` §4: lo que aprenda aquí se corrige en el contrato
**antes** de tocar el segundo motor. Este documento es el plan; nada se implementa hasta que lo
apruebes.

## De dónde partimos

| | hoy | 1.0 |
| --- | --- | --- |
| Capa B | `export default { manifest, load }` | `class Rsdkv4SDK extends EngineSDK` + `Rsdkv4Play extends EnginePlay` |
| arranque | `load(config)` lo hace todo | `boot()` motor, `restart()` partida, `start()` = los dos |
| ajustes | un solo saco: `config.options` → `settings.ini` | `config` (motor) y `options` (partida), separados |
| partidas | `instance.game.saveSlots()` / `start(slot, player)` | `play.saves()` / `play.restart({ slot, player })` |
| almacén | `storageNamespace` + `persistent` + `purgeStorage()` | `storage({ namespace })` + `play.storage()` |
| conformidad | ninguna línea la comprueba | `const _c: EngineSDKClass = Rsdkv4SDK` en CI |

El código: [rsdkv4.sdk.ts](../src/rsdkv4.sdk.ts) (~790 líneas),
[rsdkv4.options.ts](../src/rsdkv4.options.ts), [rsdkv4.manifest.ts](../src/rsdkv4.manifest.ts).
Los consumidores: tres hosts, unas 65 llamadas — `src/vanilla/engine.js` (27),
`src/demo/index.html` (8), `src/craft/services/game.service.js` (8), y el resto repartido.

Los seis documentos de `docs/` ya describen el destino
([SDK-starting-game](../docs/SDK-starting-game.md), [SDK-sdk-config](../docs/SDK-sdk-config.md),
[SDK-sdk-options](../docs/SDK-sdk-options.md),

## Fase 0 — Lo que no depende de nosotros

**No se empieza la fase 1 hasta que esto esté.** Migrar antes significa escribir la cadena entera
en rsdkv4 y tirarla cuando llegue la clase base.

1. **`engine-specs` F3**: `EngineSDK` con la cadena, el congelado, la mezcla del payload y
   `boot()` idempotente implementados. Hoy todos los miembros son `abstract`, así que la clase
   base no reutiliza nada y `create()` no está garantizado que se llame.
2. **Los tres defectos de la revisión**: miembros capados (`saves?`, `saveState?`…) que TS obliga
   a implementar, genéricos cruzados entre `EngineSDK<Config, Options>` y
   `EnginePlay<Options, Config>`, y `payload: unknown` en el evento `start`.
3. **`engine-specs` F1**: la capa A a 1.0 —`contractVersion`, `config` en vez de `options`, sin
   `mountPath` ni `validate`, `capabilities.saves`— con su JSON Schema, su validador y sus tests.
   Sin esto, [rsdkv4.manifest.ts](../src/rsdkv4.manifest.ts) no se puede migrar.

En paralelo, y aquí sí depende de nosotros: **la prueba de humo del worker** (Parte 3 de la
sesión anterior). La API 1.0 nace asíncrona porque el motor va a un worker; si el callback de
audio de SDL o el input no sobreviven a `-sPROXY_TO_PTHREAD` + OffscreenCanvas, cambia el diseño,
no sólo el calendario. Se puede medir hoy, con el `load()` actual.

## Fase 1 — Partir el saco: `Rsdkv4Config` y `Rsdkv4Options`

Es el trabajo de diseño de la migración, y lo que el resto asume. Hoy las siete claves de
[`Rsdkv4Options`](../src/rsdkv4.options.ts) mezclan motor y partida en un solo objeto que acaba
en `settings.ini`.

**`Rsdkv4Config` — del motor, idéntico en Sonic 1 y Sonic 2**

| clave | hoy | notas |
| --- | --- | --- |
| `vsync` | `vsync` | `readOnly`: sólo al arrancar |
| `devMenu` | `devMenu` | |
| `engineDebugMode` | `engineDebugMode` | `readOnly`; sólo gobierna `printLog` |
| `startMenu: 'native' \| 'host'` | `skipStartMenu: boolean` | `readOnly`; el booleano invertido pasa a enum |
| `language`, `bgmVolume`, `sfxVolume`, `screenWidth`, `fastForwardSpeed`, `dimLimit`, `useHQModes` | — | nuevas: hoy no se pueden tocar |

**`Rsdkv4Options` — de la partida, lo declara el pack**

| clave | hoy |
| --- | --- |
| `slot` | `instance.game.start(slot, …)` |
| `player` | `startingPlayer` / `game.start(…, player)` |
| `stage` | `startingCategory` + `startingScene` (dos claves, y `255` como "sin fijar") |
| `spindash`, `speedCap`, `airSpeedCap`, `spikeBehavior`, `superStates`, `shieldType` | `instance.game.options()` / `setOption()` |

**El detalle que hace que esto funcione:** `writeSettings()` está dentro de
`#ifndef __EMSCRIPTEN__` ([RetroEngine.cpp:556](../.tmp/rsdkv4-wasm-build/RSDKv4/RetroEngine.cpp#L556)),
así que **en el build wasm el motor nunca reescribe `settings.ini`**. La SDK puede regenerarlo en
cada `boot()` a partir de `config` sin pisar nada del jugador, que es justo lo que exige la regla
"el SDK no persiste preferencias". Lo que el jugador cambia en el menú GAME OPTIONS del motor va
a `SData.bin`, o sea a `storage()`, que sí es del SDK. La frontera del contrato cae exactamente
donde la pone el motor.

Y desaparece el `RSDKV4_UNSET = 255`: "arrancar normal" deja de ser un valor centinela y pasa a
ser la ausencia de la clave en el payload.

**Verificación:** los dos tipos compilan, `manifest.config` se serializa, y una tabla de
equivalencias `Rsdkv4Options` (viejo) → `{ config, options }` (nuevo) para la guía de migración.

## Fase 2 — El manifest

`contractVersion`, `options` → `config` (el JSON Schema de `Rsdkv4Config`), assets sin
`mountPath` (el VFS pasa a ser interno) ni `validate`, y `capabilities`:

```ts
capabilities: { saves: 'storage', saveStates: false, screenshots: false, multiInstance: false }
```

`saves: 'storage'` es una promesa concreta: `sdk.saves()` lee `SData.bin` del namespace **en JS,
sin arrancar el wasm**. Es lo que permite a un lanzador pintar las tarjetas de las cuatro ranuras
de dos juegos sin instanciar nada — hoy hay que arrancar el motor entero para eso. Parsear
`SData.bin` desde JS es trabajo nuevo, y es el único sitio donde esta fase es más que renombrar.

**Verificación:** `make build-manifest` + el validador de `engine-specs` contra el schema 1.0.

## Fase 3 — `Rsdkv4Play`

La instancia de hoy ya tiene casi todo, con otros nombres. El mapa:

| hoy | 1.0 |
| --- | --- |
| `instance.start()` (no-op) | desaparece: `load()` ya arrancaba |
| `instance.reset()` (lanza) | `play.restart()` — y ahora sí funciona |
| `instance.pause(owner)` / `resume(owner)` | igual, pero devuelven la cadena |
| `instance.game.start(slot, player)` | `play.restart({ slot, player })` |
| `instance.game.saveSlots()` | `play.saves()` → `SaveSlot[]` con `label` y `meta` |
| `instance.game.deleteSave(slot)` | `play.deleteSave(id)` |
| `instance.game.options()` / `setOption(k, v)` | `play.options()` / `play.options({ k: v })` |
| `instance.game.players()` / `type()` | `play.options().player.enumNames` / — |
| `instance.devMenu.getStageList()` | `play.options().stage.enum` + `enumNames` |
| `instance.devMenu.loadStage(cat, idx)` | `play.options({ stage })` |
| `instance.devMenu.setPaused()` | `play.pause(owner)` / `resume(owner)` |
| `instance.persistent` / `storageNamespace` | `await play.storage()` |
| `instance.purgeStorage()` | nada: el namespace es del host, que sabe borrarlo |
| `instance.setInput(map)` | igual, encadenable |

Lo que hay que escribir de nuevo, no renombrar: **`play.config()`** (leer y escribir en caliente
volumen, idioma, `screenWidth`…, que hoy no existe), y la resolución de `ResolvedProperty` — hoy
`RsdkGameOption` da `{ key, label, value, type, values }` y el contrato quiere
`{ value, type, enum, enumNames, title, readOnly }`.

`destroy()` pasa a ser `Promise<void>` y debe emitir `exit` — que es uno de los arreglos de la
Parte 1 que quedó pendiente.

**Verificación:** `tests/types.test-d.ts` con el motor de conformidad que ya compilé en la
revisión, más la suite de conformidad de `engine-specs` cuando exista.

## Fase 4 — `Rsdkv4SDK`

Con la clase base implementada, aquí sólo queda `create(setup)`: mount, resolución de assets,
montaje del working dir, escritura de `settings.ini` desde `config`, arranque del wasm y
construcción del `Rsdkv4Play`. Es el 80 % de lo que hoy es `load()`, sin la parte de la cadena.

Traducciones directas: `dataProvider`/`settingsProvider` → thunks en `assets()`;
`storageNamespace` → `storage({ namespace })`; `canvasEl`/`attachTo`/`canvas` → `mount()`;
`persist` → desaparece (hay `storage()` o no lo hay).

Lo que se borra si la Fase 0 trajo el worker: el espejo de `SData.bin`
([rsdkv4.sdk.ts:221-260](../src/rsdkv4.sdk.ts#L221-L260)), `web_opfs_supported()`, la rama de
"avisa y cae a memoria" y el `FS.writeFile` de 40 MB.

## Riesgos

- **El worker es el riesgo de verdad**, y es de Fase 0: audio (el callback de SDL descodifica Ogg
  leyendo del pack) e input. Si cae, la 1.0 sigue en pie pero rsdkv4 no la puede implementar como
  está escrita.
- **`saves: 'storage'` obliga a parsear `SData.bin` en JS.** Si sale caro, la salida es
  `saves: 'engine'` y `sdk.saves()` como azúcar de `boot().saves()` — coherente con el contrato,
  pero se pierde el lanzador sin arranque.
- **Doce motores detrás.** Lo que aquí resulte incómodo hay que corregirlo en el contrato antes
  del segundo motor, no acumular parches locales.
- **La clase base es código que corre en el navegador de los doce.** Cuando llegue, medir lo que
  añade al bundle.

## Qué no entra

Nada de la 0.2.x se toca hasta la Fase 5: la referencia publicada, la demo y el paquete siguen
sirviendo a quien esté en `^0.1`. Y las preguntas abiertas del contrato (P2, P6, P7, P8, P9)
siguen siendo de `engine-specs`, no de aquí.

## Extensión · 2026-08-14 12:43 — Fase 0 aprobada: ejecutar la prueba de humo del worker

Aprobado el plan; empezamos por lo único que no espera a `engine-specs`. Esto es el sub-plan de
la prueba de humo (Parte 3, pasos 1-2 de la sesión anterior), con el detalle que faltaba.

### Qué se mide

Tres preguntas, en este orden. La primera que falle decide si la 1.0 se puede implementar en
rsdkv4 tal y como está escrita:

1. **¿Arranca?** `main()` en un pthread, `emscripten_set_main_loop` corriendo allí, y el juego
   pintando en un OffscreenCanvas transferido. Si el bucle no corre en el worker, no hay nada
   que medir.
2. **¿Suena?** El callback de SDL (`ProcessAudioPlayback`) descodifica Ogg leyendo del pack. Si
   SDL lo invoca en el hilo del navegador, ese `fread` no se resuelve donde vive el fichero.
3. **¿Responde?** Los eventos DOM cruzan del hilo principal a la cola del pthread — un salto por
   evento. Y `document.querySelector('#canvas')` no existe en el worker.

### Cómo, sin romper lo que funciona

La build actual se queda intacta: el interruptor es **`RSDKV4_WORKER=1`**, opt-in, en
[scripts/build.sh](../scripts/build.sh), y la salida va a `dist/rsdkv4-worker/`. Así se pueden
tener las dos builds servidas a la vez y comparar A/B sin reconstruir.

Flags que añade el interruptor:

- `-pthread -sPROXY_TO_PTHREAD -sPTHREAD_POOL_SIZE=…` — `main()` deja el hilo del navegador.
- `-sOFFSCREENCANVAS_SUPPORT=1 -sOFFSCREENCANVASES_TO_PTHREAD='#canvas'` — Emscripten hace el
  `transferControlToOffscreen()` él mismo al crear el hilo; el SDK no tiene que tocarlo todavía.

El SDK **no se migra** para esto: `load()` ya acepta `jsUrl`/`wasmUrl`, así que la página de humo
apunta al build worker y reutiliza el SDK 0.1 tal cual. Se mide el motor, no la API nueva.

### Lo que ya se sabe que va a chirriar

Anotado ahora para no confundirlo con un fallo de la prueba: **los puentes embind se llaman desde
el hilo principal** (`web_get_save_slots`, `web_start_game`…) y se ejecutarán ahí, tocando estado
del motor a la vez que el hilo del motor. Para el humo vale; la 1.0 tendrá que proxyarlos. Es
justo el tipo de hallazgo que el plan dice que hay que corregir en el contrato antes del segundo
motor.

### OPFS no entra todavía

`web_mount_opfs` lo llama el SDK por `ccall` desde el hilo principal, así que seguiría dando en
la misma aserción: montar de verdad exige hacerlo **desde el hilo del motor**, y la escritura de
los 40 MB pasa a ser del host por la API OPFS del navegador. Es la recompensa del worker, pero
es un paso aparte y no es lo que puede tumbar el plan. Primero arrancar, sonar y responder.

### Verificación

`make build-wasm-worker` + `make preview`, y la página de humo con el juego en marcha: arrancar,
oír la música de la zona, mover a Sonic. Lo que se pueda instrumentar (arranque, hilo, ritmo de
frames) lo reporta la página; audio e input los confirma el oído y el pulgar.

[scripts/build.sh](../scripts/build.sh) añade `-pthread -sPROXY_TO_PTHREAD=1
-sPTHREAD_POOL_SIZE=4 -sOFFSCREENCANVAS_SUPPORT=1 -sOFFSCREENCANVASES_TO_PTHREAD='#canvas'
-sOFFSCREEN_FRAMEBUFFER=1` y saca el resultado a `dist/rsdkv4-worker/`, intacto el de siempre en
`dist/rsdkv4/`. `make build-wasm-worker` y `make build-smoke` son los objetivos nuevos.

Confirmado en Chrome headless, sin pack: el módulo instancia en 66 ms, exporta `PThread`, tiene
**4 workers en el pool** esperando, y `callMain` resuelve a `__emscripten_proxy_main` — o sea que
`main()` se va al hilo, que era el paso 1. Ni una excepción en consola. El baseline, reconstruido
con los mismos puentes, instancia en 38 ms.

**Dos puentes nuevos**, porque las tres preguntas no se pueden contestar desde JS:

- `web_frame_count()` — `Engine.frameCount` leído del heap compartido. Dos muestras separadas un
  segundo son los FPS reales del motor, corra donde corra. Y como el contador se reinicia al
  cargar escena, una caída delata que **una pulsación llegó al motor**: ahí está la mitad
  objetiva de "¿responde?".
- `web_engine_off_main_thread()` — lo graba el propio bucle en su primer frame, porque
  preguntarlo desde JS sólo describe el hilo que pregunta. −1 sin arrancar, 0 en el hilo del
  navegador, 1 fuera. Ese bit es de lo que va todo el experimento.

Ninguno entra en `ENGINE_BRIDGES`, así que el SDK 0.1 no marca como caducadas las builds viejas.

**La página**: [src/worker-smoke/](../src/worker-smoke/), servida en `/worker-smoke/`. Instancia
el motor **directamente**, sin pasar por el SDK: lo que se prueba es el motor, y las preguntas
son sobre cosas que el SDK esconde a propósito (el handle del Module, dónde se rechaza el montaje
OPFS, el contador). Un desplegable cambia entre las dos builds. El audio se mide de verdad: un
`AnalyserNode` interceptado en `connect()` da RMS y pico, así que "no suena" deja de ser opinión.

### Extensión · 2026-08-14 13:12 — primer resultado: OffscreenCanvas y SDL2 no se hablan

Primera pulsación de Boot en `/worker-smoke/`, primer hallazgo:

```
InvalidStateError: Failed to execute 'getContext' on 'HTMLCanvasElement':
Cannot get context from a canvas that has transferred its control to offscreen.
    at _eglCreateContext
    at __emscripten_receive_on_main_thread_js
```

La transferencia **funcionó**: el canvas es del hilo del motor. Lo que no funciona es quién pide
el contexto. RSDKv4 dibuja por SDL2, SDL2 pide su contexto GL por EGL, y **la EGL de Emscripten
está proxyada al hilo principal** — ahí está `__emscripten_receive_on_main_thread_js` en la pila,
que es el salto en sí. En ese hilo el elemento ya no puede dar contexto, porque su control se
fue. Las dos mitades del paso 2 de la Parte 3 se pelean entre ellas.

No es un flag de más ni de menos: para que OffscreenCanvas sirva, SDL tendría que crear su
contexto con `emscripten_webgl_create_context()` **en el hilo dueño**, y eso es un cambio en el
port de SDL2, no en nuestras fuentes.

**Lo que cambia el plan, y lo que no.** El paso 2 (OffscreenCanvas) se separa del paso 1
(`PROXY_TO_PTHREAD`), que es el que de verdad importa: el motor en un worker es lo que hace
alcanzables los sync access handles de OPFS, y eso sigue en pie. La imagen se resuelve mientras
tanto por `OFFSCREEN_FRAMEBUFFER`, dejando el canvas en el hilo principal y proxyando las
llamadas GL. Se pierde rendimiento —lo que la sesión anterior llamó "ir a pedales"— y **ahora
tenemos cómo medirlo**: `web_frame_count()` contra la baseline.

Así que la pregunta 1 se parte en dos: *¿corre el motor en un worker?* (crítica, decide la 1.0) y
*¿a qué precio en frames?* (grave si es mucho, pero no tumba el diseño; la salida sería atacar el
port de SDL2). `RSDKV4_OFFSCREEN=1` queda como interruptor aparte, apagado, para que el próximo
intento arranque de una medición y no de cero.

### Resultado · 2026-08-14 19:05 — la prueba de humo, contestada

Medido en Chrome headless conducido por CDP, con Sonic 1 de verdad arrancando en Green Hill
Zone (`.tmp/scripts/cdp-run.mjs`, desechable). Las tres preguntas:

| | baseline | worker |
| --- | --- | --- |
| hilo del bucle | del navegador | **fuera de él** |
| fps (Green Hill, 6 s) | 58.9 – 61.0 | **59.9 – 60.0** |
| audio | suena (RMS 0.132) | **revienta al abrir el dispositivo** |
| input (Escape → dev menu) | congela | **congela igual** |
| render | SDL acelerado (WebGL) | SDL por software |

**1. ¿Arranca? Sí, cambiando de renderer.** `PROXY_TO_PTHREAD` funciona: el motor corre en el
worker y lee el pack desde allí. Lo que no funciona en ninguna de sus dos configuraciones es
WebGL:

- con el canvas transferido, `eglCreateContext` está proxyado al hilo principal y allí el
  elemento ya no da contexto;
- sin transferir, el contexto se crea en el principal y las llamadas GL del motor, que corren en
  el hilo, encuentran `GLctx` sin definir (`Cannot read properties of undefined (createShader)`).

La salida resultó ser que **este motor no necesita GL**: RSDKv4 dibuja por software y sólo pedía
`SDL_RENDERER_ACCELERATED` por costumbre. Con `SDL_RENDERER_SOFTWARE`, SDL vuelca los píxeles por
el contexto 2D —un blit por frame de 320×240— y el problema desaparece entero.

Y con eso cae la premisa del paso 2 de la Parte 3: **OffscreenCanvas no hacía falta**. No hay
"ir a pedales" que evitar, porque no hay una llamada GL por objeto que proxyar. 60 fps clavados,
indistinguibles de la baseline. El coste del worker en frames es cero.

**2. ¿Suena? No, y falla antes y peor de lo previsto.** No es el `fread` del Ogg cayendo en el
hilo equivocado: es que **el pegamento JS de audio de SDL2 no es consciente de hilos**. En el
pthread busca un objeto `SDL2` del lado del Module que allí no existe y lanza
`Cannot read properties of undefined (reading 'audioContext')` antes de que el motor pinte un
solo frame. Con el audio desactivado (`RSDKV4_NOAUDIO=1`, sólo para medir) todo lo demás va.

Que la medición es buena lo demuestra la baseline por el mismo instrumento: RMS 0.132, música
sonando, `ScriptProcessor` en el hilo principal. El medidor funciona; lo que no funciona es SDL
en el worker.

La salida es la que la sesión anterior daba como plan B y ahora es obligatoria: **prebufferizar
en el hilo del motor y dejar el callback como copia de un anillo** — un `AudioWorklet` en el hilo
principal drenando un buffer compartido que llena el motor. Es trabajo en `Audio.cpp`, no en el
SDK, y no toca `boot()` ni el lanzador.

**3. ¿Responde? Sí.** Con los frames avanzando, un Escape sintético congela el contador en el
acto —es el manejador del dev menu del motor— y se comporta **igual en las dos builds**. La
tecla cruza al hilo. (Mide llegada, no latencia; el juego con las flechas sigue siendo cosa del
pulgar.)

**Y el premio:** `web_opfs_supported()` sigue diciendo 0 desde la página, pero ahora hay un hilo
de motor desde el que emitir el montaje. Eso es lo que perseguía todo el experimento.

### Qué significa para el plan

La Fase 0 **no invalida la 1.0**: la API asíncrona sigue justificada y rsdkv4 puede implementarla.
Pero el precio de mudarse al worker no era el que estaba escrito:

- **Sale del plan** el paso 2 (OffscreenCanvas). No aporta nada aquí y cuesta un parche al port
  de SDL2.
- **Entra en el plan** el renderer por software: una línea en `Drawing.cpp`, ya parcheada.
- **Entra en el plan, y es el trabajo de verdad**, el anillo de audio en `Audio.cpp`. Hasta que

## Extensión · 2026-08-14 19:20 — el anillo de audio

Lo único que separa al build worker de ser publicable. No se enseña a SDL a vivir en un hilo: se
le quita el audio de las manos.

```
hilo del motor    ProcessAudioPlayback() → anillo (int16 estéreo, 44100 Hz)
hilo de audio     AudioWorklet vacía el anillo en su quantum de salida
```

**Por qué esto es más simple que lo que había**, no más complicado: el estado de audio del motor
(música, canales de sfx) sólo lo toca el hilo del motor, y la bomba corre ahí también — así que
la mezcla no necesita ni un solo candado. La única frontera entre hilos es el anillo, y es una
cola de un productor y un consumidor con dos cursores atómicos. Donde SDL tenía
`SDL_LockAudio`, aquí no hay nada que bloquear.

**Las piezas:**

- `WebAudio.cpp` — el anillo (8192 frames, ~186 ms) y `web_audio_pump()`, que el bucle llama una
  vez por frame y produce en trozos de 512 frames hasta tener ~70 ms por delante. Ese colchón es
  contra el temblor del rAF, no contra la latencia.
- `web_audio.js` — biblioteca JS enlazada con `--js-library`, con `__proxy: 'sync'`: es el
  mecanismo del propio Emscripten para que una función llamada desde el hilo del motor se
  ejecute en el principal, que es donde existe `AudioContext`. El worklet lee el anillo
  directamente de la memoria compartida por `Atomics`; nada se copia ni se postea por frame.
- El contexto se crea a **44100 Hz exactos** para que no haya remuestreo en medio.
- `Audio.cpp` deja de abrir el dispositivo SDL en el build worker y arranca el anillo en su
  lugar, por la rama de éxito — la de fallo saltaba `LoadGlobalSfx()`.

**Riesgo conocido, anotado antes de que muerda:** `web_audio_set_paused` y `web_audio_stop` los
llama el host desde el hilo principal, y ahora mutan estado que el hilo del motor está mezclando.
Antes el callback de SDL corría también en el principal y no había carrera. `StopMusic()` en
mitad de una descodificación es la peor de las dos. Para la 1.0 esos puentes tienen que
proxyarse al hilo del motor; hoy queda escrito, no arreglado.

### Resultado · 2026-08-14 20:10 — el anillo suena

Medido igual que antes, Sonic 1 en Green Hill Zone, headless conducido por CDP:

| | baseline | worker (con anillo) |
| --- | --- | --- |
| hilo del bucle | del navegador | **fuera de él** |
| fps | 53 – 60.9 | **60.0 clavados** |
| audio | `ScriptProcessor`, RMS 0.174 | **`AudioWorklet`, RMS 0.201** |
| input (Escape) | congela | congela igual |
| errores | ninguno | **ninguno** |

El worker tiene **paridad completa** con la build publicada: corre fuera del hilo del navegador,
a 60 fps, con sonido y con teclado. La baseline se reconstruyó después de todos los cambios y
sigue igual que estaba — `WebAudio.cpp` compila a un par de funciones vacías sin `-pthread`, así
que el build de siempre ni se entera.

Lo que queda por confirmar es de oído: que lo que sale es *música* y no un chisporroteo. El RMS
dice que hay señal y que tiene la forma esperada, pero no distingue una cosa de la otra.

### Lo que esto cambia en el plan

La Fase 0 termina **sin invalidar nada** de la 1.0, y con la lista de trabajo real de rsdkv4:

- ~~OffscreenCanvas~~ — sale. Este motor no usa GL: `SDL_RENDERER_SOFTWARE` y a otra cosa.
- Renderer por software — hecho.
- Anillo de audio — hecho.
- **Montar OPFS desde el hilo del motor** — es lo único que falta del experimento, y ahora hay
  dónde: un hilo de motor vivo. Es lo que perseguíamos desde el principio.
- Proxyar `web_audio_set_paused` / `web_audio_stop` al hilo del motor (la carrera anotada arriba)
  antes de que esto sea publicable.

### Medición · 2026-08-14 19:25 — cuánto lag de entrada cuesta el worker

Prioridad declarada: input lag mínimo. Los 60 fps no dicen nada de eso, así que se mide aparte.
El motor sella `performance.timeOrigin + performance.now()` en el instante en que saca el
keydown de la cola de SDL (`web_note_key_arrival`, en el `case SDL_KEYDOWN`); la página sella el
mismo reloj al enviarlo. La diferencia es el transporte. 40 pulsaciones por build, con espaciado
irregular para no caer siempre en la misma fase del frame.

| | min | p50 | p90 | max | media |
| --- | --- | --- | --- | --- | --- |
| baseline (hilo principal) | 0.37 | 9.20 | 14.57 | 17.35 | **8.41 ms** |
| worker | 0.41 | 10.17 | 14.95 | 16.10 | **9.35 ms** |

**El worker cuesta ~1 ms.** Y el detalle que lo explica todo está en el mínimo: 0.41 contra 0.37,
o sea que **el salto entre hilos en sí vale 0.04 ms**. Cuando el motor está listo para consumir,
cruzar de hilo no se nota.

Lo que domina las dos columnas no es el hilo, es el frame: una tecla que llega justo después de
que el motor haya leído su entrada espera al siguiente ciclo, y de ahí el reparto entre 0 y 16 ms.
La media teórica de esa espera a 60 Hz es 8.3 ms; medimos 8.41 y 9.35. Que los números caigan
donde la teoría dice es la mejor señal de que el instrumento mide lo que creemos.

**Lo que esto no mide, y hay que decirlo:** la salida. Que la tecla llegue al motor en 9 ms no
dice cuándo aparece el píxel. El blit se proxya al hilo principal, y si aterriza pasado el rAF en
curso la imagen se compone un vsync más tarde. Eso no es observable desde JS —la composición no
está a nuestro alcance—, así que se queda en las manos (y los ojos) de quien juegue.

**Si algún día ese lado molesta**, la salida óptima ya está identificada y ahora sabemos que es
viable: que el worker sea dueño del canvas y presente él mismo, sacándole la presentación a SDL
igual que acabamos de sacarle el audio. El motor sólo produce un framebuffer RGB565 terminado, así
que es un `putImageData` en el worker, no un port de SDL.

**Conclusión: el worker no penaliza el input lag.** Un milisegundo sobre una cuantización de
dieciséis. La decisión entre hilo principal y worker se puede tomar por lo que de verdad está en
juego —OPFS síncrono y quitarse la copia de 40 MB— sin que la respuesta del mando entre en el
cálculo.

# Extension · 2026-08-15 03h44 — Plan: full SDK rewrite against `engine-specs` 0.3.1

**Summary of what this extension adds.** `engine-specs` was rewritten upstream while this session
was measuring the worker. The contract this plan targeted (Layer A + Layer B abstract base class,
`boot()`, `saves()`, `EngineManifest`) no longer exists. This extension reads the new contract,
records what it invalidates in the phases above, and plans a complete rewrite of the SDK against
it. Nothing here is implemented yet.

## What the contract is now

`main` is at **0.3.1**: a single types-only file, `src/engine-specs.ts` (117 lines), no runtime
dependencies. Verified against the published tree, not assumed.

- **Layer A is deleted.** No `EngineManifest`, no `JSONSchema`, no `schema/`, no `validate`, no
  `capabilities`. Engine identity survives as **statics on the constructor**
  (`EngineSDKConstructor`: `id`, `version`, `name?`, `description?`), so a launcher reads
  `Rsdkv4SDK.id` without constructing anything.
- **Four payloads, one type parameter.** `P extends EnginePayloads` closes `config`, `options`,
  `assets`, `storage` at once.
- **Read and write are one method with two overloads.** `config(patch)` writes and chains;
  `config()` returns `Promise<PropertiesDefinition<P['config']>>` — a descriptor per key
  (`value`, `default?`, `description?`, `live?`, `enum?`, `allowedTypes?`). The descriptor shape is
  never accepted on write. `live: true` means the key applies to the running session; absent or
  `false` means it needs a `restart()`.
- **`EngineSurface`** = those four plus `mount(target)`. Every carrier exposes it: the factory, the
  live engine, and the chainable promise.
- **`start(options?)` is the only way in.** `boot()` was removed from the contract on 2026-08-15;
  implementations keep a private `#boot()` and `start()` is `#boot()` + `restart()`.
- **`PromisePlay` is structural**, not a `Promise` subclass: `then`/`catch`/`finally` delegating to
  an inner promise, plus `[Symbol.toStringTag]`, plus the whole `EngineSurface` and
  `restart`/`destroy` so a host can chain before the engine exists.

Two reference engines implement it upstream and are type-checked in CI:
`tests/engine.conformance.ts` and `demo/demo.sdk.js`. The rewrite copies their idioms —
`arguments.length === 0` to tell a read from `config(undefined)`, and a `hydrate()` function for
the chainable promise — rather than inventing its own.

## What that does to the phases above

| phase | state |
| --- | --- |
| **Fase 0** | done, and it fed back into the contract: `mount()` is now neutral about how the picture reaches the page, which is our SDL2/OffscreenCanvas finding |
| **Fase 1** (split `config` / `options`) | **survives unchanged** — it is the design work, and 0.3.1 wants exactly that split |
| **Fase 2** (the manifest) | **dead**. `EngineManifest` does not exist. `src/rsdkv4.manifest.ts`, `dist/manifest.json`, the `./manifest` export and `make build-manifest` have no contract behind them |
| **Fase 3** (`Rsdkv4Play`) | survives, retargeted: no `saves()`/`deleteSave()` on the contract surface, `ResolvedProperty` becomes `PropertyDefinition`, `destroy()` is already `Promise<void>` |
| **Fase 4** (`Rsdkv4SDK`) | survives, and grows: there is no base class, so the chain is ours to write |
| **Fase 5** (hosts) | unchanged in nature, larger in blast radius |
| **Fase 6** (publish) | `peerDependencies` targets `^0.3.0`, not `^1.0` |

**Saves: settled.** `capabilities.saves: 'storage'` left with Layer A, and with it the plan to parse
`SData.bin` from JS so a launcher could paint four slots without booting. Decision: **the UI owns
that.** No pre-boot save API is written. The live-engine bridges stay (see below), because a host
rendering start screens needs them from a running engine anyway.

**`boot()` is gone, and we are the engine that paid for it.** rsdkv4 boots on a pthread and reads
its pack there, so the seam between "pay the startup cost" and "open a session" was worth something
here. It stays private: `#boot()` inside `Rsdkv4SDK`, `start()` = `#boot()` + `restart()`. If a
host ever needs to pay it early, that is the contract decision to reopen upstream, not a local
patch.

## The shape to write

```ts
interface Rsdkv4Payloads extends EnginePayloads {
  config: Rsdkv4Config;    // the engine: read at boot, mostly not live
  options: Rsdkv4Options;  // the session: what a restart() opens
  assets: Rsdkv4Assets;    // the pack and the settings file
  storage: Rsdkv4Storage;  // where saves live
}
```

**`config` — the engine.** `vsync`, `devMenu`, `engineDebugMode`, `startMenu: 'native' | 'host'`
(the inverted `skipStartMenu` boolean becomes an enum). All `live: false`: the engine reads
`settings.ini` at boot and, because `writeSettings()` is inside `#ifndef __EMSCRIPTEN__`, never
writes it back — so the SDK can regenerate the file on every boot without overwriting anything the
player owns.

**`options` — the session.** `player`, `slot`, `stage`. The `RSDKV4_UNSET = 255` sentinel
disappears: "boot normally" becomes the absence of the key. The engine's own GAME OPTIONS rows
(`web_get_game_options` / `web_set_game_option`) are the `live: true` half of this payload, and
their descriptors are built from the engine at read time — which is what makes a settings screen
paintable without the host knowing a single key name.

**`assets`.** `data` (the `Data.rsdk` pack, `allowedTypes: ['.rsdk']`) and `settings`
(`['.ini']`). Both accept a **thunk** as well as bytes, which is where `dataProvider` /
`settingsProvider` go: `assets({ data: () => fetch(...) })`, resolved on a cache miss only, so the
tens of megabytes are still not fetched when a copy is already persisted.

**`storage`.** `namespace` (today's `storageNamespace`, same normalisation) and `persist`
(today's `persist: null` — the host wanting nothing kept). `purgeStorage()` does not come back: the
namespace is the host's choice and the host can clear it.

**Classes.** `Rsdkv4Play implements EnginePlay<Rsdkv4Payloads>` — the live engine, owning the
Emscripten module, the pause ownership rule, the save mirror and this engine's own extras
(`game`, `devMenu`, `pause(owner)`, `resume(owner)`, `setInput`). `Rsdkv4SDK implements
EngineSDK<Rsdkv4Payloads>` with the four statics and a private `#boot()`. A local `hydrate()`
builds the structural `PromisePlay`.

**The line that goes in CI**, and the point of all of it:

```ts
const _contract: EngineSDKConstructor<Rsdkv4Payloads> = Rsdkv4SDK;
```

| --- | --- |

# Extension · 2026-08-15 04h10 — Correction: 0.3.2 ships events **and** the base classes

**Summary.** The extension above was written against 0.3.1 and is already out of date. `0.3.2`
(published, and what `main` carries) adds two things that between them delete most of the work the
previous plan described: an **event channel** on `EngineSurface`, and the **base classes** the
`PLAN-1.0.md` era wanted, this time shipped as optional structural helpers rather than a wall of
`abstract`. Scope decided with the user: **the SDK only** — the three hosts migrate in a later
change.

## What 0.3.2 adds

**Events.** `on(type, listener)` / `off(type, listener)` on every carrier, an `on: {…}` map in
`EngineInit`, and a shipped `EventEmitter` — the package's only runtime code. The listener receives
`{ type, detail }`, frozen, *not* a DOM event: it does not bubble, cannot be cancelled, has no
target. `CoreEvents` is what every engine emits and none declares:

| event | detail |
| --- | --- |
| `start` | `Partial<Options>` — the options the session opened with; a `restart()` emits it too |
| `error` | `Error` — emitted **and** rejected, always both |
| `exit` | `void` — `destroy()` has settled |
| `pause` / `resume` | `{ owner: string }` |

`pause`/`resume` carrying an **owner** is our own pause-ownership rule, now standard. Note what the
contract does *not* have: methods to trigger them. `pause(owner)` stays this engine's own member,
and emits the core event.

An engine declares its own events with the new optional `events` member of `EnginePayloads`, which
`EventsOf<P>` unions with the core set. So the shape asked for in this session —

```js
play.on('saves', ({ detail: saves }) => { /* … */ })
```

— is expressible as written: `events: { saves: Rsdkv4SaveSlot[] }`, emitted from `Rsdkv4Play`.

**Base classes.** `EngineSDKBase`, `EnginePlayBase`, `hydratePlay()`, and `EngineSpec` —
`PropertiesSpec<T>` being the descriptors *without* `value`, since the value is state. They are
optional (the contract stays structural), but they already implement the chain, the cumulative
flat merge, the descriptor assembly, the one-engine-per-factory rule, the `error`-both-ways rule,
and the channel shared between factory and session. A subclass supplies:

| member | rsdkv4's |
| --- | --- |
| `createPlay(init, events)` | build `Rsdkv4Play` |
| `open(options)` | boot the wasm if needed, then start the game at `{ player, slot, stage }` |
| `close()` | today's `destroy()` body |
| `mounted(target)` | the canvas work: id, tabindex, listeners, `fitPicture` |
| `patched(kind, patch)` | apply the `live` keys — the GAME OPTIONS rows — and ignore the rest |
| `EngineSpec` | the two descriptor tables, passed up through `super()` |

`seed()` builds starting state from each descriptor's `default`, which kills the duplication the
previous plan had left in: `DEFAULT_RSDKV4_OPTIONS` and a `default:` in the schema were two copies
of the same values with nothing checking they agreed.

**One thing the base class cannot do for us.** `#describe()` is private and reads a spec fixed at
construction, but rsdkv4's interesting enums are only knowable after the pack is loaded — the
stage list, the playable characters, and the GAME OPTIONS rows, which differ between Sonic 1 and
Sonic 2. So `Rsdkv4Play` **overrides `options()`** to enrich the inherited descriptors with what
the engine reports. That is the one place this engine does not simply inherit.

## Correction on the OPFS premise

Half right, and the half that is wrong decides the design. Today:

- **`Data.rsdk` is in OPFS because the host put it there** — `src/vanilla/storage.js` and
  `src/craft/services/opfs.service.js` both write `rsdkv4/<Game>/Data.rsdk`. The SDK reads bytes
  the host hands it and writes them into the wasm FS.
- **`SData.bin` is in OPFS because the SDK mirrors it there** ([rsdkv4.sdk.ts:262-291](../src/rsdkv4.sdk.ts#L262-L291)),
  into that same `<namespace>/` folder. The engine's own working dir is OPFS-backed *only* when
  `web_opfs_supported()` says so — an Asyncify/JSPI build, which today's is not — so on the shipped
  build the working dir is in-memory and the mirror is the only reason a save survives a reload.

So the UI can indeed read `<namespace>/SData.bin` without the engine, and should. But it can only
read it because the SDK writes it. **Decision: the mirror stays, and gains the event.** The SDK
owns getting the bytes out of the wasm and into the namespace both sides already agree on; the UI
owns reading, parsing and painting them. `play.on('saves', …)` is what tells it when to look
again, so it no longer has to poll or guess.

That also settles where the mirror is triggered from: today it is a 10-second timer plus pause plus
`destroy()`. With an event to emit, the same three moments emit `saves` after writing.
