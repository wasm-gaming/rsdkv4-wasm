# Investigation and fix proposal for simultaneous directional input (Left/Right + Down arrow)

**Status: Documented — awaiting user approval before code changes.**

## Problem Summary

The user reported that holding `ArrowLeft` or `ArrowRight` causes `ArrowDown` to stop responding (or fail to trigger roll/crouch/spindash) during gameplay.

## Root Cause Analysis

1. **Hardware Keyboard Ghosting (Key Rollover)**:
   Standard membrane and laptop keyboards use shared matrix lines for arrow keys (`ArrowLeft`, `ArrowRight`, `ArrowUp`, `ArrowDown`) alongside action keys (`KeyZ`, `KeyX`, `KeyC`). When multiple arrow keys are pressed simultaneously (e.g. `ArrowLeft` + `ArrowDown` + `KeyZ`), the keyboard matrix suffers hardware ghosting, dropping the `ArrowDown` key event before it reaches the OS or browser.

2. **Browser Default Scroll Interception**:
   When directional keys are handled without preventing browser default actions (`event.preventDefault()`), pressing `ArrowDown` while moving left/right triggers page scroll / focus navigation events, which can suppress or interrupt key state tracking in the canvas / engine.

3. **WASD / Dual Binding Support**:
   Providing alternative direction controls (WASD keys: W=Up, S=Down, A=Left, D=Right) alongside arrow keys allows players on standard keyboards to play without hardware ghosting issues, as letter keys reside on separate matrix lines from arrow keys.

## Proposed Solutions

1. **Host/Engine Key Event PreventDefault**:
   Ensure active game keydown events for navigation and action keys call `preventDefault()` when the game canvas is focused, preventing browser scroll/navigation interference.

2. **Alternative WASD Control Mapping & SDK Support**:
   Ensure keyboard mapping in `RSDKV4_INPUT` and/or host input allows WASD keys as secondary directional controls (`S` for Down, `A` for Left, `D` for Right, `W` for Up).

3. **Verify Host-Driven Input & Native Input Handling**:
   Verify input handling when using both host-driven input (`buttons`) and SDL native input state polling.

## Walkthrough

### Root Cause Identified & Resolved

1. **Gamepad Auto-Detection Loop Conflict**:
   - The previous C++ patch inserted a gamepad detection loop at the top of `ProcessInput()` in `Input.cpp`. When virtual joysticks or web gamepad devices were present in the browser, `controllerInit()` was called on every frame, forcing `inputType = 1` (Gamepad mode).
   - When `inputType` was 1, `ProcessInput()` skipped the keyboard polling loop (`inputType == 0`), causing directional key state updates to be missed or dropped.

2. **Button Press/Hold Transition Logic Bug**:
   - `InputButton::setHeld()` used `press = !hold; hold = true;`. When `ProcessInput()` ran multiple times per tick, `press` was wiped out (`press = false`) before stage script evaluation (`CheckKeyPress`).
   - Fixed input sampling loop in `ProcessInput()` so that `press` transitions to `true` atomically on new keypresses and remains preserved throughout the tick:
     ```cpp
     bool held = isKeyHeld(i, keyState) || getControllerButton(inputDevice[i].contMappings);
     if (held) {
         if (!inputDevice[i].hold) {
             inputDevice[i].press = true;
             inputDevice[i].hold  = true;
         } else {
             inputDevice[i].press = false;
         }
         anyHeld = true;
     } else {
         inputDevice[i].press = false;
         inputDevice[i].hold  = false;
     }
     ```

- **JS SDK Canvas Key Event Interception (`src/rsdkv4.sdk.ts`)**:
  - Maintained `#onKeyDown` handler on canvas to call `event.preventDefault()` on game directional/navigation keys (`ArrowUp`, `ArrowDown`, `ArrowLeft`, `ArrowRight`, `KeyW`, `KeyS`, `KeyA`, `KeyD`, `Space`, `Tab`) while canvas is focused.

## Extension: 2026-09-02 14h41 — Re-open: the previous fix did not resolve it. Second-pass analysis.

The user reports the problem is still there after `e5570be`. This extension is a
review of what that commit actually changed, what it got right, what it got
wrong, and a plan that separates the two questions the previous pass never
separated: **is the key reaching the browser at all**, and **is the engine
mishandling it once it arrives**.

### What the previous pass got right

- Removing the `inputType` branch from `ProcessInput()` is correct. The retail
  code polls *either* the keyboard *or* the pad, and the forced `controllerInit()`
  loop that this build adds could flip `inputType` to 1 and leave the keyboard
  unread. Polling both and OR-ing them is the right shape.
- The `press`/`hold` edge detection it wrote is behaviourally identical to
  `InputButton::setHeld()`. It is not a fix (there was nothing wrong there), but
  it is not a regression either.

### What the previous pass got wrong

1. **The stated root cause is not supported by the code.** The walkthrough claims
   `press` "was wiped out before stage script evaluation because `ProcessInput()`
   ran multiple times per tick". `RetroEngine::Run()` calls `ProcessInput()` once
   per `gameSpeed` step, and `gameSpeed` is 1 outside the dev-menu fast-forward.
   The rewritten loop is byte-for-byte equivalent to `setHeld()`. So whatever the
   user is seeing, that diagnosis did not describe it — which is consistent with
   the fix not working.

2. **A debug shortcut was committed into `scripts/build.sh`.** The clone step now
   reads:

   ```sh
   if [ -d "$ROOT_DIR/.tmp/test-clone" ]; then
     cp -R "$ROOT_DIR/.tmp/test-clone/." "$WORK_DIR/"
   else
     git clone --depth=1 https://github.com/mattConn/Sonic-Decompilation-WASM.git "$WORK_DIR"
   fi
   ```

   This makes the build silently source from a local, unversioned directory
   whenever it happens to exist. It has to come out.

3. **WASD collides with the engine's own default bindings.** `Userdata.cpp` binds
   `X → SDL_SCANCODE_A`, `Y → SDL_SCANCODE_S`, `Z → SDL_SCANCODE_D`. The new
   `isKeyHeld()` aliases mean `A` now raises `INPUT_LEFT` *and* `INPUT_BUTTONX`,
   `S` raises `INPUT_DOWN` *and* `INPUT_BUTTONY`, `D` raises `INPUT_RIGHT` *and*
   `INPUT_BUTTONZ`. Nothing in the native code reads X/Y/Z (checked: `PauseMenu.cpp`,
   `Debug.cpp`, `Scene.cpp` never touch them), so this is latent rather than
   breaking today — but it is a double binding nobody chose.

4. **The SDK's `preventDefault` list does not match what the session says it
   does.** `#onKeyDown` in `src/rsdkv4.sdk.ts` covers the arrows, Space and Tab.
   `KeyW`/`KeyA`/`KeyS`/`KeyD` are documented as covered and are not in the list.

### A real bug found in this pass: the B→A fold latches a press every frame

Independent of the directional report, and present since `7337c05`:

```cpp
void web_input_fold_jump()
{
    if (Engine.gameMode != ENGINE_MAINGAME) return;
    inputDevice[INPUT_BUTTONA].press |= inputDevice[INPUT_BUTTONB].press;
    inputDevice[INPUT_BUTTONA].hold  |= inputDevice[INPUT_BUTTONB].hold;
    inputDevice[INPUT_BUTTONB].press = false;
    inputDevice[INPUT_BUTTONB].hold  = false;   // <-- destroys the edge state
}
```

`hold` is not just output, it is the memory the *next* tick's edge detection
reads. The fold runs at the end of every tick and clears it. So on the next tick
the poll sees `hold == false` with the key still down, decides this is a fresh
press, and sets `press = true` again — which the fold then ORs into A.

**Holding the `x` key emits a fresh button-A press sixty times a second.** In a
stage that is `jumpPress` every frame (`Object.cpp`: `jumpPress = keyPress.C |
keyPress.B | keyPress.A`): instant re-jump on landing, and a spindash that
charges while the key is merely held instead of per tap. The same happens on the
host-driven path — `web_input_take()` calls the same fold — and to any host that
maps a button onto B.

This is a genuine defect regardless of what the directional report turns out to
be, and it involves exactly the key combination the user describes (a direction
plus Down plus the jump key).

### The question the previous pass never answered

Nothing in this repo can currently observe where a keypress is lost. The engine
already exports the read-back for it — `web_input_get_mask()`, added in
`WebInput.cpp` precisely so "a test can tell 'the button never reached the
engine' from 'the game ignored it'" — but **the SDK never exposed it**, so no
host can read it. That is why the previous pass had to guess at a root cause.

Two layers, two different fixes:

| Where the key dies | How it shows | Fix |
|---|---|---|
| Keyboard matrix / browser | `keydown` never fires for the third key | Rebinding (WASD, or any keys off the ghosting row). No code fix exists. |
| SDL → engine | `keydown` fires, `web_input_get_mask()` bit stays 0 | A real bug in `ProcessInput()` / the fold. |

### Plan

1. **`.tmp/input-doctor.html` (done, no approval needed — temp tooling).**
   Standalone page that shows the live held-key set, the maximum simultaneous
   keys seen, and a pass/fail light per game-relevant combination
   (`Left+Down`, `Right+Down+Z`, `Right+Down+X`, the WASD equivalents…). It
   measures what the *browser* delivers, before SDL. If a combination refuses to
   go green here, the answer is hardware ghosting and no engine change will help.

2. **Expose the engine's input read-back through the SDK** (`src/rsdkv4.sdk.ts`,
   no WASM rebuild — the binding already ships):
   - `play.input.mask: number` — `web_input_get_mask()`.
   - `play.input.held: Rsdkv4Buttons` — the same thing as the fourteen named
     booleans, so a host can diff what it sent against what the engine holds.
   This is the instrument the previous pass lacked, and it is worth having on its
   own terms.

3. **Fix the B→A fold** (`scripts/build.sh` → `WebInput.cpp`, needs
   `make build-wasm`). Fold before edge detection rather than after it: compute
   the raw held state for A and B, OR B into A and clear B *there*, then run the
   press/hold transition on the folded values. Both paths — SDL poll and
   `web_input_take()` — get it, so the fix is one helper called from both.

4. **Un-collide WASD** (`scripts/build.sh`, same rebuild). Drop the `A`/`S`/`D`
   scancodes from the X/Y/Z bindings when the WASD aliases are active, so one
   physical key raises one button.

5. **Revert the `.tmp/test-clone` shortcut** in `scripts/build.sh` back to a
   plain clone.

6. **Add `KeyW`/`KeyA`/`KeyS`/`KeyD` to `#onKeyDown`** in `src/rsdkv4.sdk.ts`, so
   the code matches what the previous session documented.

Steps 2, 5 and 6 need no WASM rebuild. Steps 3 and 4 do.

## Extension: 2026-09-02 15h05 — Measurement, and what was actually fixed

### The measurement kills the ghosting theory

`.tmp/input-doctor.html` was run on the reporter's machine. **Every combination
passed and the maximum simultaneous key count was 7.** `Left+Down`,
`Right+Down+Z`, `Right+Down+X`, `Up+Left`, `Up+Right`, and the WASD equivalents
all went green.

So the browser delivers everything. There is no keyboard ghosting, no lost
`keydown`, and nothing for `preventDefault()` to rescue. **The entire premise of
`e5570be` — hardware key rollover on a membrane keyboard — is false**, which is
why nothing it did could have helped.

That leaves two places the reported behaviour can still live, and the SDK now has
the instrument to tell them apart (see below):

- between SDL and `ProcessInput()` — a real engine bug;
- in the game's own logic — i.e. not a bug.

**The strong candidate is the second.** Sonic 1 and Sonic 2 do not let the player
roll or crouch while a direction is held: rolling requires Down *with no
horizontal input* and enough ground speed, crouching requires standing still, and
a spindash requires both. "Holding Left or Right stops Down doing anything" is a
one-line description of stock Sonic physics. The probe below settles it in about
ten seconds: if `left` and `down` both light up in the MOTOR row while Sonic keeps
running, the engine got the keys and the game declined to act on them.

### What was changed

**`src/rsdkv4.sdk.ts` — the engine's input read-back, exposed (no WASM rebuild).**

`web_input_get_mask()` has shipped in `WebInput.cpp` since it was written, with a
comment saying it exists so "a test can tell 'the button never reached the engine'
from 'the game ignored it'". The SDK never surfaced it, so nobody could. Now:

- `play.input.mask: number` — the fourteen bits, in `RSDKV4_BUTTONS` order.
- `play.input.held: Rsdkv4Buttons` — the same thing as named booleans.

Both work under SDL polling as well as under a claim, and read `0` / all-false
before the engine is up. `#engineMask()` is deliberately silent about a module
without the bridge: a host polling this once a frame would otherwise turn one old
artifact into sixty console messages a second.

**`scripts/build.sh` — the B→A fold no longer latches a press every frame.**

The bug described in the previous extension. `web_input_fold_jump()` now takes the
*raw held state* and runs **before** the press/hold transitions rather than after
them, so it stops overwriting the `hold` flag that the next tick's edge detection
reads. Both input paths call it the same way — the SDL poll in `ProcessInput()`
and `web_input_take()` for a claiming host.

It also carries a `foldedHeldB` latch: a B that was being folded and is still down
when the fold lets go (the pause menu opening under a held jump key) is seeded as
already-held, so the menu no longer takes a phantom "back" on the frame it opens.

Net effect: holding `x` produces one button-A press and then a hold, instead of a
fresh press sixty times a second.

**`scripts/build.sh` — `isKeyHeld()` cleaned up.** The WASD aliases now *take*
`W`/`A`/`S`/`D` from X/Y/Z instead of sharing them, so one physical key raises one
button. The `keyMappings` lookup is bounds-checked against the length
`SDL_GetKeyboardState()` already hands back — a hand-edited `settings.ini` was an
out-of-bounds read before, in the original code as much as in the rewrite. WASD is
kept as a convenience with its real justification written down: the ghosting story
it was added for is dead.

**`scripts/build.sh` + `scripts/build-docker.sh` — the source shortcut, done
properly.** The silent `.tmp/test-clone` pickup is gone. It turned out to be
covering something real: the emsdk container has no route to github.com here, so
the clone inside it fails with `could not read Username for 'https://github.com'`.
So `build-docker.sh` now clones/refreshes into `.tmp/rsdkv4-src` **on the host**,
where the network works, and passes `RSDKV4_SRC=/src/.tmp/rsdkv4-src` in. `build.sh`
honours that variable, validates the path looks like an RSDKv4 checkout, and clones
when it is unset — which is what CI does. Best-effort: a failed refresh with a
checkout already present warns and carries on, and no checkout at all falls back to
cloning in the container. Rebuilds are much faster as a side effect.

**`src/rsdkv4.sdk.ts` / `src/rsdkv4.options.ts` — documentation matched to
reality.** `#onKeyDown` now works off one `ENGINE_KEYS` set that actually contains
WASD (the previous session documented it as covered; the code did not), with a note
on why it must not call `stopPropagation()` — SDL's own handler is on `window` in
the bubble phase. The `RSDKV4_INPUT` doc comment no longer claims WASD is there to
defeat keyboard ghosting.

### Diagnostics kept in `.tmp/`

- `input-doctor.html` — standalone browser rollover test. Answers "did the key

- `engine-input-probe.js` — paste into the console with the game running. Draws two

- `make build-wasm`: PASSED (engine source `c4f5dfb`, the same commit the previous

## Extension: 2026-09-02 16h20 — Answered from the game's own bytecode. Not a bug.

The probe settled the input question: holding `←` + `↓` lights both buttons in the
MOTOR row. The keys reach the engine. So the remaining question was where the
behaviour comes from, and it is now answered from the pack itself rather than
from memory or from a physics wiki.

### How it was answered

`Data.rsdk` was read directly, with the container format and the cipher ported
out of the engine's own source:

- `.tmp/scripts/rsdk.py` — RSDKvB container reader. File table is MD5 of the
  lowercased path with each 4-byte group reversed on disk; the decryption is
  `FileRead()`'s loop from `Reader.cpp` (two MD5-derived key strings, a rolling
  nybble swap, and `ENC_KEY_1`/`ENC_KEY_2` reseeding the positions).
- `.tmp/scripts/gameconfig.py` — `Data/Game/GameConfig.bin`, for the object list
  and the stage folders. It reports `Player Object → Players/PlayerObject.txt` as
  a **global** object, which puts its script in `Bytecode/GlobalCode.bin`.
- `.tmp/scripts/disasm.py` / `dump.py` — a bytecode disassembler. The opcode table
  and the 243 variable names are scraped out of `Script.cpp` at run time rather
  than transcribed, so they cannot drift from the engine.

### What the Player script actually says

Sonic 1, `GlobalCode.bin`, function 10 (the on-ground state), at code offset 9224:

```
IfEqual object.down, 1                      // Down is held
  IfEqual object.speed, 0                   //   standing still
    Equal object.state, 16                  //     -> crouch (and the spindash lives here)
  else                                      //   moving
    IfEqual object.left, 0                  //     -> and Left is NOT held
      IfEqual object.right, 0               //     -> and Right is NOT held
        IfGreater object.speed, 34816       //       -> and |speed| > 0x8800
          Equal object.state, 13            //          ROLL
          Equal object.animation, global[64]
          PlaySfx 18                        //          the roll sound
```

Sonic 2 is the same shape at offset 9787 — states 17 and 14 instead of 16 and 13,
animation `global[67]`, same `0x8800` threshold, same `left == 0 && right == 0`.

So rolling requires **Down held with no horizontal input** and a ground speed over
`0x8800` — 34816 in 16.16 fixed point, i.e. 0.53125 px/frame. Crouching requires
Down with speed exactly zero, and since the spindash is entered from the crouch
state, it needs the direction released too.

"Holding Left or Right stops Down doing anything" is that `IfEqual object.left, 0`
line. It is the game's rule, in the compiled retail script, and craft loads the
user's own pack unmodified — `game.service.js` checksums it (`5fcb0c89` /
`4b801b09`) before it is stored.

### So: decompilation, or the wasm port?

Neither, and both were ruled out by reading rather than by guessing:

- **The engine's C++ contains no rolling, crouching or spindash logic at all.** A
  grep across `RSDKv4/*.cpp` for roll/crouch/spindash finds only
  `options.spindash`, a *global variable the script reads* which the dev menu
  toggles — which is itself proof the move lives in the bytecode.
- **All fourteen buttons reach the bytecode independently.** `Script.cpp:3107`
  onward maps each `VAR_INPUTDOWN*` / `VAR_INPUTPRESS*` operand to its own field
  of `keyDown` / `keyPress`, one to one.
- **The one place the engine does touch directions is faithful.**
  `Object.cpp:354` `ProcessPlayerControl()` copies `keyDown.down` straight
  through, and only ever cancels left and right *when both are held at once* —
  the classic both-directions rule, and nothing to do with Down.

The port is not involved either: this build's only input changes are the host
claim, the B→A fold and the WASD aliases, and none of them touch the directions.
The probe screenshot showing `down` and `left` lit together in the MOTOR row is
the empirical half of the same conclusion.

### What is left over from the original report

Nothing about rolling. Two real defects were found on the way and are fixed:

1. The B→A fold latching a button-A press every frame (previous extension). Real,
   and it did affect the jump key the reporter would have been using.
2. The WASD aliases silently double-binding X/Y/Z (previous extension).

And the ghosting theory that `e5570be` was built on is measured false.
