# Host-driven input, and the jump key that pauses

**Status: Planned — awaiting approval before any code changes.**

Scope only: what gets implemented. The investigation that led here is not reproduced.

---

## Why

Pressing `x` makes Sonic jump *and* opens the pause menu. Measured cause: `x` is button **B**,
and B carries two meanings at once. Jump is the engine's, by design — `Object.cpp:367`,
`jumpPress = keyPress.C | keyPress.B | keyPress.A`. Pause is the **game's**: the retail
bytecode inside `Data.rsdk` pauses on B as well as on `start`, and only the script interpreter
ever writes `ENGINE_INITPAUSE` (`Script.cpp:5064` → `RetroGameLoop.cpp:51`). The engine never
pauses on its own.

So it is not fixable at the source — that code is compiled and encrypted in the pack. The fix
is to stop feeding B. Verified by measurement: the pause follows the **logical button**, not
the physical key (remap B onto `v` and `v` pauses instead), in both Sonic 1 and Sonic 2, and
with craft's exact config.

Separately, the SDK has no input API at all: `setInput()` writes a global nobody reads. A host
that wants to own input — touch buttons, rebinding, netplay, tests — has no way in.

---

## 1. Engine patch: fold B into A while a stage runs

New patch in `scripts/build.sh`, at the end of `ProcessInput`:

```c
// The retail bytecode welds the pause to button B, and B is also a jump button — so on a
// keyboard the jump key pauses. Fold B into A while a stage is running. The dev menu
// (ENGINE_DEVMENU) and the pause menu (ENGINE_WAIT) run under other gameModes and keep B
// as their "back".
if (Engine.gameMode == ENGINE_MAINGAME) {
    inputDevice[INPUT_BUTTONA].press |= inputDevice[INPUT_BUTTONB].press;
    inputDevice[INPUT_BUTTONA].hold  |= inputDevice[INPUT_BUTTONB].hold;
    inputDevice[INPUT_BUTTONB].press = inputDevice[INPUT_BUTTONB].hold = false;
}
```

**The `ENGINE_MAINGAME` guard is load-bearing.** `keyPress.B` is "back" in the native dev menu
(~10 sites in `Debug.cpp`) and in `PauseMenu.cpp:119`; clearing B unconditionally leaves both
menus with no way out.

Chosen over remapping the defaults because it is the only option that **costs no key** (`z`,
`x` and `c` all keep jumping — the engine's table is 1:1, so dropping B from it would leave
only two jump keys), **covers the gamepad for free** (B's `contMappings` is
`SDL_CONTROLLER_BUTTON_B`, so the east button jumps and pauses today too), and **needs nothing
from the host**.

Known risk, accepted: a pack that used B for something else in-stage would lose it. Sonic 1 and
2 do not. Gate it behind a `settings.ini` key if that ever matters.

Ships on its own. Independent of everything below.

## 2. Replace the dead export

`RSDKV4_KEYMAP` (`src/rsdkv4.sdk.ts:102`) has never been checked against the engine, because
nothing reads it — `setInput()` writes `window.__gamepadKeyMap`, which has no consumer in the
repo or in `node_modules`. It shows: only 9 of the 14 buttons (`x`, `y`, `z`, `l`, `r`
missing), `select: 'ShiftLeft'` where the engine default is `Tab`, and a
`Record<string, string>` type that accepts any key name.

- Delete `setInput()` and `Rsdkv4KeyMap`.
- Export `RSDKV4_INPUT = { keyboard, gamepad }`, complete and correct, typed by a
  `Rsdkv4Button` union so TypeScript catches at compile time the same typos `claim()` catches
  at runtime.
- Its meaning changes: no longer engine config, but a **default table for the host to build its
  key handler from**. Craft needs exactly that.

The 14 buttons, with the engine's defaults for reference:

| button | key | scancode | pad | value |
| --- | --- | --- | --- | --- |
| up / down / left / right | Arrow* | 82 / 81 / 80 / 79 | DPAD_* | 11 / 12 / 13 / 14 |
| a | `KeyZ` | 29 | A (south) | 0 |
| b | `KeyX` | 27 | B (east) | 1 |
| c | `KeyC` | 6 | X (west) | 2 |
| x / y / z | `KeyA` / `KeyS` / `KeyD` | 4 / 22 / 7 | Y / ZL / ZR | 3 / 22 / 23 |
| l / r | `KeyQ` / `KeyE` | 20 / 8 | shoulders | 9 / 10 |
| start | `Enter` | 40 | START | 6 |
| select | `Tab` | 43 | GUIDE | 5 |

Sonic 1 and 2 read only up/down/left/right, A, B, C and start. The other six are free.

## 3. `options({ buttons })` — the host drives

```js
const buttons = $reactive({
  up: false, down: false, left: false, right: false,
  a: false, b: false, c: false, x: false, y: false, z: false,
  l: false, r: false, start: false, select: false,
})

const play = new Rsdkv4SDK()
  .mount(canvas)
  .assets({ data })
  .options({ buttons })     // exclusive takeover
  .start()

play.options({ buttons: null })   // release: the engine polls SDL again
```

Named sugar over the same payload: `play.input.claim(buttons)` / `play.input.release()`.

**On the `options` payload, not a new method or `config`.** `options` is in `hydratePlay`'s
fixed literal, so it works on an un-awaited `start()`, chains, and survives `restart()` through
the cumulative merge; and it is the only payload `patched()` handles today
(`rsdkv4.sdk.ts:574-576`). A new method would need a wrapper around `Rsdkv4SDK.start()` and
explicit re-application on restart.

### Mechanism: pull, not push

The engine calls into JS once per tick, at the top of `ProcessInput`; the SDK reads the host's
object at that moment and returns a mask.

```c
int inputSource = 0;    // 0 = SDL, 1 = host
if (inputSource == 1) {
    hostInputMask = web_input_pull();
    for (int i = 0; i < INPUT_ANY; i++) {
        if (hostInputMask & (1 << i)) inputDevice[i].setHeld();
        else if (inputDevice[i].hold)  inputDevice[i].setReleased();
    }
    return;                       // NB: also skips the inputType autoswitch
}
```

Pull removes a whole class of problem: no second sampler and therefore no added phase error, no
write/poll race, no coalescing, and any object works — a plain one, a jq79 `$reactive` store —
without the SDK knowing anything about reactivity. Cost is one wasm→JS→wasm hop per tick.
Precedent for engine-calls-JS: `RSDKv4/web_audio.js`.

**The `return` is load-bearing.** Without it the autoswitch at the end of `ProcessInput` hands
control back to SDL the moment a real key or pad button is touched.

Optional, and worth having: **latching**. A tap shorter than a frame is dropped today; with the
host owning the state the SDK can hold "was set since the last read" for one tick and lose none.

### Bridges to add

| bridge | for |
| --- | --- |
| `web_input_set_source(int)` | claim / release |
| `web_input_pull()` — EM_JS, returns a mask | the per-tick read |

Bridges rather than exporting the `inputDevice` pointer: a raw pointer couples the SDK to the
12-byte struct layout, and a future field on `InputButton` would make the SDK write garbage in
silence.

## Hazards to handle

1. **`claim()` validates strictly**: exactly the 14 keys, missing *and* unknown both fatal. The
   first sketch of this API lost `Right` to a duplicated `Up` — a duplicate key in an object
   literal is silent in JS, and surfaces as an absent key.
2. **A missing key reads as falsy, silently.** The failure falls the safe way: a key that
   disappears leaves a **dead** button, never a **stuck** one. No attempt to detect absence —
   telling "missing" from "false" needs an `in` per key, and on a jq79 store that lies (its
   `has` trap returns `true` for deleted keys, by design).
3. **Do not seal the host's object.** Sealing a Proxy is invariant-sensitive and `$reactive`
   returns one. Sealing is the host's one-liner on plain objects; the SDK does not reach into
   the host's data structure. TypeScript covers the literal; `claim()` covers the shape.
4. **`try/catch` around the pull, throttled.** It runs 60×/s. Emit on the **first** occurrence,
   then at most **once per second** while the same error repeats, with a count *since the last
   emission*. Keep retrying — do **not** auto-release: a transient fault recovers on its own,
   whereas releasing changes input ownership behind the host's back. Return `0` (all released)
   while failing, never the last good mask — a repeated mask with buttons held leaves the
   character running on its own. Key sameness on `` `${err.name}: ${err.message}` ``. No timer:
   compare `performance.now()` inside the `catch`. Reset key and counter on the first success,
   so a relapse announces itself immediately.

   ```js
   let lastKey = null, lastEmit = 0, since = 0
   // …in the pull's catch:
   const key = `${err?.name}: ${err?.message}`
   const now = performance.now()
   since++
   if (key !== lastKey || now - lastEmit >= 1000) {
     this.emit('error', { where: 'input.pull', error: err, occurrences: since, windowMs: now - lastEmit })
     lastKey = key; lastEmit = now; since = 0
   }
   return 0
   ```

   *What can actually throw:* with a plain object, nothing — the guard is inert. It exists
   because the API accepts **any** object, and a Proxy runs host code on every read: the
   reference stops being an object (the host's component unmounts, nulls its store and never
   called `release()` — by far the most likely case), a revoked `Proxy.revocable`, a `get` trap
   throwing after its effect scope was torn down, a host getter whose backing is gone. Claim-time
   validation does not cover any of these: it validates once, over a live reference.

   *Open, deliberately unresolved:* a **permanent** fault leaves the controls dead with one
   error per second explaining why — legible, but unplayable. A safety net would be releasing
   after N seconds of continuous failure. Not included unless asked for.
5. **`null` and `undefined` must differ.** Absent means "leave it alone"
   (`rsdkv4.options.ts:117`); only `null` releases. If the cumulative merge treats them alike, a
   later `options({ stage })` silently drops the claim.
6. **`buttons` is live and non-persistable**, and must stay out of session-picker UIs. The
   getter form of `options()` is meant to return serialisable state — a host doing
   `JSON.stringify(await play.options())` must not sweep 14 transient booleans into saved
   settings. And `options` descriptors are what a host reads to paint "choose a save /
   character / stage". Mark it in the descriptor on both counts.
7. **Lost keyup is now the host's problem.** SDL resets its keyboard on focus loss; a host that
   owns input inherits that job (`blur`, `visibilitychange`) or a held arrow strands the player.
8. **The gamepad becomes the host's entirely.** Under `claim()` the engine stops polling it, so
   the host must poll the Gamepad API on rAF and reimplement the deadzones and the
   D-pad-from-axes fallback that `getControllerButton` provides. This is real work in craft.
9. **The touch pause rect survives `claim()`.** `(240,0)-(424,40)` is fed from
   `touchDown`/`touchX`/`touchY`, filled in `processEvents` from mouse and finger events —
   outside `ProcessInput`. A click in the top-right of the canvas still pauses.
10. **The pull must not run inside a reactive effect.** jq79 attributes every read through a
    store's `get` trap to whichever `$effect` is running, so a pull inside one would make all 14
    buttons dependencies of that effect and every keypress would wake it. Structurally this
    cannot happen here — `trackerStack` is only non-empty during an effect's synchronous run,
    and the pull's stack is always `rAF → wasm (Run → ProcessInput) → EM_JS → our read`.
    **Invariant, not luck:** keep the pull on the engine's callback.

## Extension — 2026-08-17 01h57: all three steps implemented

Steps 1, 2 and 3 built as planned. What follows is what was written, what was measured,
and the four places the implementation departed from the plan above.

### Step 1 + 3, engine side — `scripts/build.sh`

One new file, `RSDKv4/WebInput.cpp`, registered in the Makefile SOURCES list beside
WebFS/WebAudio/WebDevMenu/WebGame. It holds both halves, because both write
`inputDevice` and both are called from the same patch:

- `web_input_fold_jump()` — the B→A fold, guarded on `ENGINE_MAINGAME` exactly as
  specified.
- `web_input_take()` — returns 1 when the host owns input, having written
  `inputDevice` from the mask `web_input_pull()` (EM_JS) returned.
- `web_input_set_source(int)` / `web_input_get_source()` — embind, the claim switch.

`Input.cpp` is patched twice, in python3 after the existing perl controller patch: the
claim goes in at the top of `ProcessInput` (ahead of the joystick scan — a host that
owns input owns the pad with it) with the load-bearing `return`, and
`web_input_fold_jump()` goes in just before the closing brace, where the SDL paths
reach it. Both patches assert their anchor is unique, and both were dry-run against
the real `Input.cpp` and `Makefile` before being committed to the script.

**Departure 1 — the fold runs under a claim too, not only on the SDL path.** The plan
put the fold at the end of `ProcessInput` and the claim's `return` in front of it,
which would have left a claiming host with the original bug: the pause is the *pack's*,
welded to the logical button, so a host that maps a jump button onto `b` hits exactly
the same thing. `web_input_take()` therefore calls the fold before returning. Menus are
unaffected either way — the `ENGINE_MAINGAME` guard is what decides that, not the path.

**Departure 2 — `INPUT_ANY` and the dim timer are maintained under a claim.** The
plan's sketch looped `i < INPUT_ANY` and returned. But `Engine.dimTimer` is only ever
touched inside `ProcessInput`, so returning early would have left the screen dimming
under a claim however busy the player was. The host path now mirrors what both SDL
paths do with `INPUT_ANY` and `dimTimer`.

Also: `web_input_set_source()` clears every button on both edges of a transition. The
losing side's held buttons are otherwise still down in `inputDevice`, and the winning
side never sees the release that would clear them.

### Step 2 — `RSDKV4_INPUT` replaces `RSDKV4_KEYMAP`

`Rsdkv4KeyMap`, `RSDKV4_KEYMAP` and `setInput()` are gone, along with the
`this.setInput()` call in `#boot()`. Nothing in the repo read any of them.

In their place, in `rsdkv4.options.ts` (not `rsdkv4.sdk.ts` — `buttons` is an options
key, so the vocabulary has to live where the payload does; both are re-exported from
the SDK entry point, so the public import path is unchanged):

- `RSDKV4_BUTTONS`, the 14 in engine order — which is the mask's bit order, so the
  array is the wire format and not just a list.
- `Rsdkv4Button`, derived from that array rather than declared beside it, so there is
  one list and not two to drift.
- `Rsdkv4Buttons = Record<Rsdkv4Button, boolean>`.
- `RSDKV4_INPUT: { keyboard, gamepad }`.

**Departure 3 — `gamepad` carries browser button indices, not SDL's.** The plan's table
lists `SDL_CONTROLLER_BUTTON_*` values (dpad 11-14, shoulders 9/10, start 6). Those are
the right numbers for `settings.ini`, and the wrong ones for a host: hazard 8 hands the
gamepad to the host under a claim, the host polls `navigator.getGamepads()`, and SDL's
left shoulder is 9 where the browser's standard mapping puts Start. Shipping SDL's
numbers would have had every claiming host's shoulder button open the pause menu. So
`gamepad` is translated to standard-mapping indices — through this build's own
web-gamepad mapping string, which is what the engine itself translates with — and
`select` is `null`, because RSDKv4 binds it to SDL's GUIDE and that mapping string
never wires GUIDE up. It is dead on a pad in the engine today, and saying so is better
than a number that does nothing. `y` and `z` are 6/7, the analog triggers, matching
`getControllerButton`'s ZL/ZR-past-a-deadzone handling.

### Step 3 — `options({ buttons })`

`Rsdkv4Options.buttons?: Rsdkv4Buttons | null`, with a spec entry marked `live: true`.
On `Rsdkv4Play`: `#buttons` (the host's object, by reference), `#applyButtons()` as the
only writer, `#readButtons()` as the per-tick read, and `play.input` —
`claim()` / `release()` / `claimed` — as named sugar over the same payload.

Wiring, all three hooks: `patched()` applies a claim *ahead of* its `!this.#module`
early return, so a malformed claim is rejected by the call that made it rather than by
a boot three lines later; `open()` re-applies from the merged state, which is what
carries a claim through `restart()`; `close()` releases first thing, so the ticks the
engine takes on its way down do not reach into a host object whose owner has been told
the session is over.

Hazards 1-7 and 10 are implemented as written. Two notes on how:

- Hazard 5 (`null` ≠ `undefined`) is a `buttons !== undefined` test rather than an
  `in` test. Same result, and it does not have to reason about the base class merging
  an explicit `undefined` in as a value.
- Hazard 6 (not persistable, not a settings row): the contract has no descriptor flag
  for "transient", so `#describeOptions()` overwrites `value` with `null`
  unconditionally — claimed or not — and the description says the rest out loud.
  `play.input.claimed` is the honest question and is deliberately a different one. **If
  the contract ever grows a `transient` flag, this is the first thing that wants it.**

**Departure 4 — latching is not implemented.** The plan called it optional and worth
having. It cannot be done honestly on a pull-only design: a tap that begins and ends
between two pulls is one the SDK never observed, so there is nothing to latch. Doing it
properly means the SDK owning a `press()` the host calls, which is a second API and a
push channel — worth a session of its own, not a footnote in this one.

`make typecheck` and `make build-sdk` clean.

`.tmp/scripts/input-smoke.mjs`, 18 checks, all passing — the reachable half of the

## Extension — 2026-08-17 02h30: built, measured in a browser, and one premise corrected

The wasm is built and both halves are verified in headless Chrome against a real
Sonic 1 pack. 24 browser checks and 18 node checks, all passing. This extension also
**corrects the "Still to verify" list in the 01h57 entry above**, and corrects one thing
the original plan assumed.

### The build

`make build-wasm` clean. `WebInput.cpp` compiles and links, `web_input_pull`'s EM_JS
body is in the glue with its `Module["__rsdkv4_input_pull"]` lookup intact, and the
embind names are in the wasm. The C++-linkage pairing between `Input.cpp`'s
declarations and `WebInput.cpp`'s definitions is right — a mismatch there would have
been a link error, and was caught by reasoning before the first build rather than after.

### Two bridges added that the plan did not call for

Diagnosing the pause (below) needed observability that did not exist, and both
additions are small and permanently useful rather than test scaffolding:

- `web_input_get_mask()` — which buttons the engine has held, in the pull's own bit
  order. The read-back to the pull's write: a host can confirm its claim is arriving,
  and a test can tell "the button never reached the engine" from "the game ignored
  it", which are otherwise the same silence.
- `web_engine_game_mode()` — `Engine.gameMode`, so a caller can tell a running stage
  (`ENGINE_MAINGAME`) from a menu (`ENGINE_WAIT`, `ENGINE_DEVMENU`).

### The premise that did not hold: the pause does not fire in this harness

**The frozen-frame test in the plan's Verification section cannot answer the question
here, and the reason is worth recording.** `Engine.frameCount` is bumped at the end of
`ProcessStage()`, which only runs under `ENGINE_MAINGAME`, so it is a sound pause
detector. It never froze. Measured, in Green Hill Zone 1, on the shipped pack:

- pressing `Enter` puts `start` in the engine's mask — the button unquestionably
  arrives — and the game stays in `ENGINE_MAINGAME`;
- the same through a host claim (`buttons.start = true`, no keyboard involved at all)
  also arrives, and also does not pause;
- via the dev-menu stage warp *and* via `game.start()`, with `startMenu` `'host'` and
  `'native'`.

So the retail pause never fires in this setup, on `start` or on anything else, and a
"does not pause" reading proves nothing. Two earlier readings that looked like results
were both artifacts and are recorded here so nobody re-derives them: a first pass ran
in stage list **0**, which is Presentation — the title screen and the level select,
where there is no pause object at all — and a first Escape probe read as "froze" only
because it sampled while the stage was still loading.

Whatever the pack wants before it will pause, this harness does not give it. Since the
original symptom was measured in a real host session, the likely difference is the
`nativeEntityCount > 1` bail at `ENGINE_INITPAUSE` — but that was not chased, because
it stopped mattering once the measurement moved.

### What replaced it, and why it is stronger

`web_input_get_mask()`. It reports **what the engine received**, where a pause that did
not happen only reports that a pause did not happen. For step 1 this is strictly the
better instrument: the pause-on-B lives in the pack's bytecode and cannot fire on a
button that was never delivered, so "B never reaches the game in-stage" *is* the fix,
and it is now a direct reading rather than an inference from an absent symptom.

### What was measured — `.tmp/scripts/input-check.mjs`, 24 checks

Step 1, in GREEN HILL ZONE 1:

- `x` — button B, the jump key that pauses — arrives as **`a`**, with B cleared;
- `z` still arrives as `a`, `c` still as `c`, `Enter` still as `start`: no key was
  spent on the fix, exactly as the plan required;
- in the native dev menu, **B survives and still works as "back"** — the
  `ENGINE_MAINGAME` guard holds. This one needed per-frame sampling to measure at all:
  B in the dev menu *exits* the dev menu, on the first frame the menu sees it, so any
  reading taken afterwards lands back in the stage where the fold applies and answers a
  different question. Sampling per rAF and watching the mode go 0 → 1 catches both
  facts at once — B was set (impossible if the fold had cleared it, as the in-stage
  trials show, where B never appears once) and the menu obeyed it.

Step 3, with a plain object and with a jq79 `$reactive` store, identically:

- `claim()` takes and the engine reports `source = 1`;
- a **physical** `Enter` while claimed leaves the mask empty — the takeover is
  exclusive, the engine really has stopped polling SDL;
- the host's `right` and `start` arrive as `right` and `start`;
- the host's `b` arrives as `a` — the fold covers a claiming host too, which is
  departure 1 from the 01h57 entry, now measured rather than argued;
- `release()` gives it up, `source` returns to 0, and a physical `ArrowRight` moves the

## Extension — 2026-08-17 02h45: the CI had not caught up with the manifest removal

Asked whether CI would pass. The two jobs in `build.yml` are fine for this session's
work — and the `wasm` job especially, since `bash scripts/build.sh` in
`emscripten/emsdk:latest` is exactly the command and exactly the image the build was
verified in locally. But the workflows still referenced `src/rsdkv4.manifest.ts` and
`scripts/emit-manifest.mjs`, both deleted when the SDK moved to the contract, and two of
those references were breakages rather than stale prose.

**Two things that would have failed a release:**

- `release.yml`, bump job: `git add package.json package-lock.json src/rsdkv4.manifest.ts`
  — `git add` on a path that does not exist errors, so the bump would have failed after
  a successful build, taking the release, npm and pages jobs with it. Now
  `src/rsdkv4.sdk.ts`, which is the third place `sync-version.mjs` actually writes.
- `release.yml`, pages job: the layout check required `dist/manifest.json`, which is no
  longer emitted at all, and `dist/demo/demo.js`, which is `dist/demo.js`. Now checks
  the seven paths the site really has, verified against a real `dist/`.

**And one gap the split left behind.** Pages deploys `dist/`, but the sdk job only ran
`make build-sdk` — which since the package/site split produces `dist/rsdkv4/` and
nothing else. No `index.html`, no `coi.js`, no hosts. The deployed site had no home
page. `build.yml` now runs `make demo` as well, and deliberately **after** `npm pack`:
that target is also the only thing that type-checks the hosts, and the Makefile's whole
reason for splitting the two was that a host which had not caught up must not block the
package release. Packing first keeps that property.

`make demo` had been failing, which is why it was never in CI. The cause was two lines
in `src/demo/start-screens.ts`: it imported `Rsdkv4Instance`, a type the contract
migration removed. Every member it actually uses — `devMenu.getStageList()`,
`game.players()`, `game.saveSlots()`, `game.start()`, `pause(owner)` — exists on
`Rsdkv4Play` unchanged, so the fix was the type name and nothing else. `make demo` is
green, and CI can now build the site it deploys.

Not touched: the three typedoc warnings about `Rsdkv4LoadConfig`, `load` and
`Rsdkv4Instance` in `README.md`. The README still documents the pre-contract API in
places, which is a bigger job than this one and belongs with whatever revisits it.

**Suggested commit message:** `ci: drop the removed manifest from the workflows and build the site again`
